## 背景

dev 今天的基本形态是多 agent 加 git worktree：每个任务一个 worktree 和分支，检查、评审之后合进 main 并推送。简单的项目只想要单线程：一个 agent，在自己的目录里改，不想先学 worktree、分支、合并。

## owner 已定（2026-11-22）

1. **仓库对话可以就地工作**：对话直接在主 clone 里写，不开 worktree。要做。
2. **用户一步一步往上走，每一步是一次设置**，起点是第 1 步：
   1. 对话就地工作。
   2. 需要 flow 时：任务在主 clone 里走 flow（就地的 flow）。
   3. 再进一步：任务各有 worktree，一次一个。
   4. 提高并发：今天的工作方式。
3. **"在哪里工作"这个设置的两个值是：主 clone 里的新分支，或 worktree**（owner 2026-11-22）。就地的任务不直接改当前分支：dev 在主 clone 里为任务开一个新分支，任务在那个分支上工作；worktree 照今天的做法。对话在第 1 步不开分支（第 10 条）。
4. **用词**（owner 2026-11-22，待决 1 已定）：设置 `workIn`，写在 `.operad/dev.json`，标题 Work in / 工作位置；值 `branch`（A branch in this folder / 本目录的新分支）和 `worktree`（A separate worktree / 独立的 worktree）。四步不单独起名。
5. **Setup Dev 让用户选**（owner 2026-11-22，待决 6 已定）：项目起始的提示词（dev 的 Setup Dev guide，`packages/dev/skills/setup/SKILL.md`，以及 `docs/user/setup-prompt.md`）要写清 `branch` 和 `worktree` 的区别（在哪里改、并发、能不能边让 agent 改边自己用这个目录、合并方式），由 bot 问用户选哪一个，写进它提议的 `.operad/dev.json`。问法要让用户看得懂，和提示词里"用我写给你的语言回复"一样：bot 用用户的语言、用平常话讲两种做法对用户有什么不同（例如"agent 在你这个文件夹里开一个新分支改，一次一件事；你在它改的时候最好不要同时改这个文件夹" 对 "每件事在单独的文件夹里做，可以同时做几件，你的文件夹不受影响"），不要求用户懂 clone、worktree、并发这些词；`branch`、`worktree` 只出现在它写的 dev.json 里。
6. **就地的任务开始时工作区不干净就拒绝**（owner 2026-11-22，原待决 2）：不开始，并说出是哪些文件。
7. **就地的任务被 reject 或 cancel 时任务分支留着**（原待决 3），和 worktree 的任务一致。
8. **任务占着主 clone 时，仓库对话的回复只读，并说明原因**（原待决 4）。
9. **两种方式都保留 gate worktree**（原待决 5 和检查在哪跑）：检查和评审照今天的做法，对着任务分支上的提交、在 gate worktree 里跑，评审报告也在那里，不写进用户的目录。第 2 步评不评审，只看 flow 有没有评审阶段，不另设规则。
10. **就地的对话在当前分支上工作，不开对话分支**（原待决 7）。
11. **branch 方式下，等人决定、可以合并、暂停的任务一直占着主 clone 的名额**，直到合并、取消或被拒（A）。并发是 1，所以此时不开第二个任务。
12. **`dev.json` 在一次尝试开始时读一次并记下来**（B）：就地时主 clone 在任务分支上，读到的是任务分支的版本，所以以尝试开始时记下的为准，不在中途重读。
13. **pool 仍然是必需的**（D）：第 1 步也要开 pool 插件。
14. **没有 git 也能用**（owner 2026-11-22，原话"还是开任务的时候需要git吧，没有git可以对话。并且改动项目内的文件"）：没有 git 的文件夹可以加进来、可以对话，对话可以改里面的文件；开任务才需要 git。
15. **电脑上没装 git 时，开任务之前什么都不问**（owner 2026-11-22，原话"开任务的时候吧，用户需要可以按现有的agent模式，不开任务的，通过会话完成任务"）。没装 git 和文件夹里没有 git 是同一个起点：只用对话。检测 git 不能在加文件夹时把系统的安装框弹出来（macOS 没装命令行工具时 `/usr/bin/git` 会弹框；先用 `xcode-select -p` 之类判断，未核实）。
16. **operad 不内置 git**（owner 2026-11-22，"不内置git"）。开任务时没装 git，bot 带用户装。怎么带是提议（operad-c4，owner 未逐条确认）：按系统给命令（macOS `xcode-select --install`，Windows `winget install Git.Git`，Linux 用包管理器），bot 要跑的每条命令都是人批准的待处理项；开任务时用大白话说"开任务需要 git，还没装"和下一步；doctor 和 dev 的 setup 检查也列出这一项。

未定（问了 owner）：

- git 仓库的子目录（monorepo 的一个包）：先拒绝并提示加仓库根目录（lead 建议），还是支持。
- 有 git 但还没有任何提交：任务分支需要起点提交，代码里怎么处理没有核实。

## 提议的形状（草稿）

### 两个设置，不是四种模式

四步可以只用仓库的两个设置表达：

| 步 | 在哪里工作 | 并发 | 用户做的事 |
|---|---|---|---|
| 1 | 主 clone | 1 | 只用对话 |
| 2 | 主 clone | 1 | 开始建任务 |
| 3 | worktree | 1 | 改"在哪里工作" |
| 4 | worktree | 2 以上 | 提高并发（已有的 `concurrency`） |

- 新设置只有一个：在哪里工作（主 clone 或 worktree）。名字是新的用户词，等 owner 定（待决 1）。
- 第 1 步和第 2 步的设置相同，区别只是用户有没有开始用任务；所以从 1 到 2 不用改设置，只要 flow 能在主 clone 里跑。
- 约束：在主 clone 工作时并发只能是 1；把并发设成 2 以上而还在主 clone 时拒绝，并说先改哪一个设置。
- 检查命令在四步里是同一份 `dev.json`，往上走不用重新配置。

### 第 1 步：对话就地工作

- 仓库设成在主 clone 工作时，仓库对话的访问档（plan、ask、edits、full）直接作用在主 clone，不再出现 worktree 的提问，提到 edits 或 full 也不开 worktree。
- 设成 worktree 时和今天一样（ADR 0028 D3 原文）。
- 要改 ADR 0028 D3：只读是"在 worktree 工作的仓库"的规则，不是所有仓库的规则。

### 第 2 步：就地的 flow

硬规则不取消，也不换成别的说法：**改动只经 integrate 到 main**。branch 方式下任务分支在主 clone 里，dev 在 worker 之后提交到任务分支，检查对着那个提交在 gate worktree 里跑，integrate 切回起始分支并快进。检查不过，起始分支上没有任何提交。要改 ADR 0020 D3、D4 的措辞（已写，见 0020）。

要解决的问题：

1. **开头**：不建 worktree。工作区不干净就拒绝并说出文件（已定第 6 条）；还要记下起始分支，结尾切回。
2. **分支和提交**（按已定第 3 条）：开头 dev 在主 clone 里从 main 开任务分支并切过去；worker 不自己提交，dev 在任务分支上提交，沿用 `commit: true` 的做法（ADR 0020 D9）；检查（和评审、人的决定）通过后合进 main 并切回 main。合并沿用 integrate，只是不在 worktree 里。没有 remote 或设置不推送时不推送。
3. **检查在哪跑**：不变，仍对着任务分支上的提交、在 gate worktree 里跑（已定第 9 条）。
4. **评审**：不变，报告仍写在 gate worktree 的 `.operad/review/` 下，用户的目录里没有报告；有没有评审只看 flow 有没有评审阶段。
5. **返工**：回到 code 阶段，在同一个工作区里继续改。
6. **reject 和 cancel**：切回起始分支，任务分支留着（已定第 7 条）。改动都在任务分支的提交里，main 不受影响，不再需要在工作区里撤改动。
7. **崩溃后继续**：worktree 可以丢掉重来，主 clone 不行。从记录知道停在哪个阶段，工作区是什么样就从什么样继续。
8. **`changed the main checkout` 的检查**：今天 worker 改了主 clone 会被记成 major finding。就地时改主 clone 是正常的，这条检查对就地的任务不适用。
9. **人同时在改**：防不了，也分不清是谁改的；说明写清楚：就地意味着和 agent 共用一个工作区。

### 一个主 clone 只有一个在写的

- 就地时，仓库对话的一次有写权限的回复和任务的 code 阶段互斥。任务占着主 clone 时（含等人决定、可以合并、暂停，已定第 11 条），对话的回复只读并说明原因（已定第 8 条）。
- 一次一个任务已经由并发 1 保证。

### 往上走和往回走

- 主 clone 改成 worktree：要求没有就地的任务在跑。之后对话回到今天的规则。
- worktree 改回主 clone：要求没有任务在跑、没有留着的 worktree。
- 每一步由 bot 提议、出待处理项、人批准后落盘，和 `Setup Dev` 同一套（`operad-setup-guides.md`）。什么时候提议要定，候选：用户要评审或要"检查过再提交"时提议建任务；用户想在 agent 工作时自己也用这个目录时提议 worktree；任务排队时提议提高并发。
- `Setup Dev` 给新仓库的起点是第 1 步。已有的仓库不变，等于第 3 或第 4 步。

## 没有核实的

- 代码已读（T-0713）：见 `docs/research/2026-11-22-dev-worktree-dependence.md`（逐处 file:line、`workIn: "branch"` 在每处要什么、任务顺序和大小、待决 2 至 7 各自代码的倾向）。要点：gate worktree 和评审报告不依赖任务的 worktree，可以原样保留；`changed the main checkout` 的检查在就地时自己失效；集成前要先切回起始分支，否则主 clone 不会被快进；等人决定的任务今天不占并发名额，就地时要改；`.operad/dev.json` 就地时读到的是任务分支的版本（已定第 12 条：开始时读一次并记下）；没有 remote 的仓库今天在第一次 fetch 就失败（约 25 处）。
- ADR 0028 D2 把 radian 排除在仓库对话之外，理由是它不能在调用开始前拦住；主 clone 可写之后这个理由还成不成立，没有想清楚。
- 调研（T-0713）说"检查在主 clone 里对着工作区跑"是另一种设计；已定第 9 条取 gate worktree，所以不需要核实这一点。pool 在第 1 步仍要开（已定第 13 条）。

## 验收

- 新仓库走完 `Setup Dev` 之后：在对话里让 agent 改一个文件，改动出现在主 clone 的工作区里，全程没有 worktree 的提问。
- 同一个仓库建一个任务：code 在主 clone 的任务分支上跑，检查在 gate worktree 里对着任务分支的提交跑。检查不过时，起始分支上没有新的提交；过了并 integrate 之后，起始分支上多了任务的提交。
- 工作区不干净时建任务被拒绝，说出哪些文件。
- reject 或 cancel 一个就地的任务：回到起始分支，用户原有的文件没有丢，任务分支留着。
- 任务占着主 clone 时，仓库对话的回复只读并说明原因。
- 改成 worktree 之后行为和今天一样（现有测试全过）；还在主 clone 时把并发设成 2 被拒绝并说明原因。
- 从第 1 步走到第 4 步，`dev.json` 里的检查命令没有改过。

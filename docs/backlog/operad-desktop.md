# operad-desktop：桌面应用

- 状态：decided（方向和第一版范围；标「建议」的是讨论里由 lead 提出、owner 没有逐条确认的，开 task 前再问一次）
- 涉及 ADR：0014（D2、D4、D5）、0029（D1、D2）、0017（D4）、0018（D2、D3）、0020（D1、D2、D4、D6）、0012（D2、D4）、0026（D10）、0030（D4、D5）
- 涉及：`operad-presentation.md`（三个客户端的样子）；`operad-plugins.md`（决定 2 的 `operad plugin add <git 地址>`）；`operad-bot.md`；`operad-dev-flows.md`
- 来源：2026-11-14 和 owner 的讨论；同日在本机做的 Electrobun 原型；Orca（stablyai/orca）和 bb（get-bb/bb）两个同类应用的技术栈（2026-11-14 读）

## 背景

operad 现在有三个客户端：命令行、TUI、iOS。三个都要求用户先在终端里装好 bun 和 operad，再自己启动 `operad serve`。不熟悉终端的人进不来。

桌面应用是第四个客户端，给这些人用：装一个应用就能开始，应用自己把 serve 跑起来。它不是 IDE：Orca 和 bb 都内嵌终端和编辑器，范围大一个量级，这里不做。

## 决定（已定，还没做）

### 给谁用、以什么为中心

1. **给不熟悉 TUI 的普通用户用。** 不假设用户会用终端。
2. **以对话和管理 flow 为中心。** 默认首页是对话。
3. **默认连本机，也可以连远程的 serve**（像手机配对那样填地址和 token）。2026-11-14 owner：第一次启动的"在哪里运行"一步默认选本机；应用先找本机已经在跑的 serve，有就直接连，没有就启动一个；点了"另一台机器"才出现地址和 token 输入框（设计稿 `03-where`、`03-where-remote`）。
4. **应用启动时自动启动 serve，并且能停止和重启它。**

### 技术栈

5. **壳用 Electrobun。** 它的主进程是 Bun 上的 TypeScript，和 operad 同一个运行时，仓库保持单一语言。Tauri 2 的壳要写 Rust；Electron 要自带 Chromium，安装包 100 MB 以上；GPUI 是 Rust 的原生界面框架，没有现成的 Markdown 和 mermaid 渲染。
6. **界面是一个 web 客户端，TypeScript 加 React**（建议）。内容只有 Markdown（ADR 0014 D2），浏览器渲染最省事。bb 的选型可以参考：react-markdown、remark-gfm、mermaid、`@pierre/diffs`。
7. **启动 serve 复用 TUI 现有的逻辑**（建议）：`packages/tui/src/autostart.ts` 的 `ensureServer`（探测，已有就不再启动第二个，没有就启动并等它应答）和 `discover.ts` 的 `discoverServer`。原型里直接 import，没有重写。
8. **serve 独立于应用运行**（建议）：关掉窗口不停 serve，下次打开直接连上。停止和重启是用户在应用里明确做的动作（决定 4）。
9. **应用自带 operad 和运行时**（建议）。普通用户不会先去装 bun 和 `@operad-io/cli`。这带来一个要解决的问题，见待决 3。

### 第一版要走通的两条线

10. **a 线，flow**：
    - 添加一个目录（现有的 `operad dev repo add`），用系统的文件夹选择框。
    - 添加后配置 operad：选一个 agent 自动跑 `docs/user/setup-prompt.md` 的提示词，写出 `.operad/dev.json`，把它选的检查命令列给用户确认（做法是建议）。
    - 看这个 repo 有哪些 flow 和每个 flow 的阶段。
    - 在界面里新建和编辑 flow。
    - 建 plan 和 task 时选 flow；在 pending、running 和对象页面里跟进和操作。
    - 浏览目录里的文件，先只看主目录。
11. **b 线，个人助理**：新建 bot、起名、选 agent 和模型；和它对话，带附件；管理它挂的 MCP 服务；bot 对自己的修改走提议，人批准后生效（ADR 0030 D4）。
12. **两条线共用的部分**：首次启动引导（检查本机有没有可用的 agent，没有就说怎么装和登录）；serve 的状态、日志、启动、停止、重启；设置表单（全局和每个 repo 两层，ADR 0017）；bot 列表挂在设置下（ADR 0018 D3）；菜单栏图标显示 pending 数量；系统通知。
13. **还要能管理 agent**：每种 agent 的数量上限和默认模型（ADR 0021 D2 的设置），以及它是否已安装和登录。

### flow 编辑器

14. **flow 编辑器是一个阶段列表，不画图**（建议）。ADR 0020 D2 规定 flow 是有序的阶段列表，只有 work、check、review、human 四种，所以界面是可增删、可排序的列表，每个阶段一张参数表单。
15. **保存时由 `dev` 校验**（建议）：ADR 0020 D4 的两条硬规则不通过就不写，界面显示 `dev` 给的原因。客户端自己不重复实现规则。
16. **TypeScript 写的 flow 只读**（建议）（ADR 0020 D6）：显示它有哪些步骤，提供“在编辑器中打开”。

### 文件浏览

17. **只读**（建议）：文件树加查看，带语法高亮和 Markdown 预览，加“在编辑器中打开”和“在 Finder 中显示”。不做编辑。
18. **应用直接读本机磁盘，serve 不加读文件的接口**（建议）。ADR 0014 D2 规定内容只有 Markdown，文件树不走那条路。所以连远程时没有文件浏览。

### 第二版

19. **安装插件从填 npm 包名开始。** 不做可浏览的插件列表。
20. **连远程时的管理功能放第二版**（建议）：添加目录、插件、密钥在远程下都需要新接口。

### 不做

21. 内嵌终端、代码编辑器、可编辑的文件树（建议）。

### web ui（以后做）

22. **先做桌面应用，web ui 放后面。**（owner，2026-11-14）
23. **web ui 和桌面应用是同一份界面代码**（建议）。界面只通过 serve 的 `/v1` 接口读写，不直接碰磁盘和进程；`operad serve` 自己提供这份界面，浏览器打开 serve 的地址就是 web ui。桌面应用是壳加同一份界面。
24. **界面和壳之间有一个小的宿主能力接口**（建议）：启动和停止 serve、系统文件夹选择框、读本机文件、填密钥、菜单栏图标。界面启动时问宿主有哪些能力，没有的功能就隐藏。桌面壳实现全部，浏览器里没有。所以第一版写界面时就按这个边界分开，壳的功能不直接写进界面里。
25. **web ui 的功能范围等于桌面应用连远程 serve 时的范围**（建议）。两者走同一条代码路径。

### 内置插件和其他插件

26. **内置插件可以有专门的页面，其他插件走通用界面。**（owner，2026-11-14）operad 仓库里的插件都算内置，这条对桌面应用、TUI 和 iOS 都适用（owner，2026-11-14）。桌面应用可以为它们写专门的界面（`dev` 的添加目录和 flow 编辑器、`chat` 的对话页、`bot` 的 bot 页、`pool` 和各个 agent 插件的 agent 管理）。第三方插件和用户生成的插件通过通用的对象接口显示：类型、列表、对象页面、动作表单、设置表单都由插件声明，客户端不用更新就能用。这要改 ADR 0029 D2。
27. **专门的页面仍然只通过 serve 的接口读写**（建议）。ADR 0029 D2 的前一半（只有一个后端）不变；改的只是“不认识任何插件”。
28. **专门的页面不可用时退回通用界面**（建议）：内置插件被停用、或它的版本比应用认识的新时，对象仍然能用通用页面打开，不报错。
29. **安装插件前有确认页**（建议）：列出包名、版本、它声明的类型、动作、要的密钥和依赖，和 bot 登记 MCP 服务的确认（ADR 0031）是同一种做法。
30. **生成插件是一次对话**（建议）：用户说要什么，agent 写出插件并跑 `operad plugin check`，然后 pending 里出现一项“启用这个插件”，人批准后生效。`operad-plugins.md` 已定“由 agent 替用户写插件是主路径”；客户端只用到对话、pending 和插件列表。生成的步骤默认在沙箱里跑、项目级插件只在信任的项目里加载，这两条不变。

### 插件自己的界面（下一个项目）

31. **插件可以带自己的界面。**（owner，2026-11-14）做法是 operad 的三个界面（桌面应用、TUI、iOS）给插件提供一个界面组件库。这是桌面应用之后的下一个项目，不在第一版里。这要改 ADR 0014 D5。
32. **开始做时单独开一个 backlog 条目**（建议）。在那之前，桌面应用的通用界面先用一套自己的组件写（列表、对象页面、动作表单、设置表单），以后把这套组件开放给插件，不另写一套。

### 第一批（2026-11-14 owner：按 lead 建议）

33. **第一批要求本机已经装好 operad。** 自带 operad 单独做一个计划，那时再定待决 3。
34. **第一版只做 macOS。**（待决 7）
35. **界面测试用 `happy-dom` 和 `@testing-library/react`**（开发依赖），壳的逻辑用 `bun:test`。真窗口的端到端测试第一批不做。
36. 决定 6–8 按建议执行（界面用 React；启动 serve 复用 TUI 的 `ensureServer` 和 `discoverServer`；关掉应用不停 serve）。
37. **设计稿是视觉模版**（`operad-desktop` 仓库 `docs/design/`）：具体实现和用词以 iOS 客户端和 operad 现在的约定为准；两边都没有的新词先问 owner。

## 原型结果（2026-11-14，macOS arm64，Electrobun 2.0.6）

一个 Electrobun 窗口，主进程调用 `ensureServer` 和 `discoverServer`，然后读 `/v1/types` 显示在窗口里。代码没有进仓库。

| 场景 | 结果 |
|---|---|
| 新 home，没有 serve 在跑 | 应用启动了 serve，226 ms 后连上 |
| 应用退出后 | serve 还在监听 |
| 再次打开，serve 已在跑 | 4 ms 连上，没有启动第二个 |
| 已有 serve 的真实 home | 7 ms 连上 |
| 正式安装包 | dmg 32 MB，解压后 92 MB |

没有验证的：

- Linux 和 Windows 没有测。Electrobun 在 Linux 上用 WebKitGTK，有第三方文档说多个 webview 的布局需要打包 CEF。
- 原型是从终端启动的。从 Finder 启动的应用拿不到登录 shell 的 PATH，serve 会找不到 `bun`、`claude`、`git`，这一点没有覆盖。
- 窗口里有一条 `Failed to initialize encryption` 的报错，来自 Electrobun 注入的脚本，用内联 HTML 加载时出现。页面正常显示，没有查它在正式页面下是否还出现。
- Electrobun 的构建工具 Hutch 安装时会往 `~/.zshrc` 加一行 PATH。检查主机和开发机上装它时要注意。

## 现有接口的缺口

| 内容 | 现状 |
|---|---|
| 对话、pending、running、对象、动作、附件、设置、bot | HTTP 已有，iOS 在用 |
| 添加、列出、移除目录 | 只有命令行（`operad dev repo add` 等） |
| 读写 flow | 没有确认 `dev.json` 的 `flows` 能不能通过设置接口改；列出 flow 只有命令行 `operad flows` |
| 插件列表、启用、停用 | 只有命令行 |
| 安装新插件 | 命令行也没有 |
| 密钥 | ADR 0017 D4 规定只走 `operad secret` |
| serve 停止和重启 | 只有本机命令行 |

连本机时应用可以直接调用自带的 operad 命令，所以第一版不一定要先加 HTTP 接口；连远程时这些功能需要接口。

## 落地时要改的 ADR

ADR 只记录已经生效的决定，所以下面这些等代码合并时再改，这里只列出来：

- **0014 D4**：“三个客户端共用的 API”改成四个，加上桌面应用。
- **0029 D2**：现在只写了 iOS 应用，并且写的是“不认识任何插件”。改成：每个客户端（桌面应用、TUI、iOS）只连 `operad serve`；内置插件（operad 仓库里的插件）可以有专门的页面，其他插件通过通用的对象接口显示（决定 26）。桌面应用多出来的两件事（启动和停止本机的 serve、读本机磁盘上的文件）是壳做的，不经过客户端 API。
- **0029**：加一条说明浏览器页面和壳怎么拿到 token。
- **0020**：加一条说明客户端可以改 `dev.json` 里的 flow，以及由谁校验。
- **0017 D4**：如果待决 2 定为本机可填密钥，这里要写明。
- **0012**：第二版加“按 npm 包名安装插件”时改。
- **0014 D5**：做插件界面组件库时改（决定 31）；第一版不动。

## 待决问题（未定）

1. **界面上叫 bot 还是“助理”。** ADR 0030 里对象的名字是 bot。换成新词是新的用户可见的词，要 owner 批准。
2. **密钥怎么填。** 助理要接 Telegram 就得填 token。建议：连本机时应用在本地直接调用 `operad secret`，不经过 HTTP；连远程时不提供。这决定第一版的助理能不能接 Telegram。
3. **自带的 operad 和用户自己装的 operad 是什么关系。** 用户两边都有时用哪个版本跑 serve；应用更新后 serve 要不要跟着重启；自带的运行时（原型里是 bun 1.4.4）和本机的 bun 不一致时怎么办。
4. **`repo add` 要求目录是 git 仓库并且有 remote。** 普通用户导入一个普通文件夹会被拒绝。要不要放宽，还是界面上引导用户先建好。
5. **按 npm 包名安装插件和 `operad-plugins.md` 决定 2 的关系。** 那里定的是 `operad plugin add <git 地址>` 只 clone、不跑安装脚本。npm 安装会跑包的安装脚本，这一条的安全考虑要重新过一遍。
6. （已定，owner，2026-11-14）桌面应用是单独的仓库 `operad-io/operad-desktop`，暂不公开，本机在 `~/Code/operad-desktop`。它把 `@operad-io/tui` 当 npm 依赖来用 `ensureServer` 和 `discoverServer`。要给 serve 加的接口仍在 operad 仓库里做。
7. **要支持哪些平台。** 原型只在 macOS 上跑过。Linux 和 Windows 是否在第一版里。
8. **签名、公证和自动更新走哪里。** Electrobun 自带更新，但更新包要有地方放。
9. **文件浏览以后要不要能看某个 task 的工作目录。** 第一版先只看主目录。
10. **浏览器怎么拿到 token**（做 web ui 时再定）：让用户粘贴一次 token，还是加一个命令打印带一次性登录码的地址。后者是新的命令名，要 owner 批准。
11. **web ui 上要不要能浏览文件和填密钥**（做 web ui 时再定）：要的话 serve 得加读文件和写密钥的接口，并改 ADR 0014 D2 和 ADR 0017 D4。
12. **插件界面的组件库怎么设计**（下一个项目开始时定，见决定 31、32）：插件用什么形式描述界面，三个客户端各自怎么渲染，第一批组件有哪些。

## 建议的顺序

1. 壳、自带 operad、首次引导、serve 控制、本机和远程连接。
2. 对话和 bot，b 线走通。
3. 添加目录、自动配置、文件浏览、pending、running、对象页面。
4. flow 列表和编辑器，a 线走通。
5. 第二版：按 npm 包名安装插件、远程下的管理功能。

## 验收

在一台没有装过 bun 和 operad 的 Mac 上装应用并打开：不开终端，引导检查出本机有没有可用的 agent；serve 自己启动，状态页显示它在运行；关掉应用再打开，没有第二个 serve。在应用里停止 serve 再启动，状态跟着变。

b 线：新建一个 bot，和它对话并发一个附件；它提议给自己加一个 MCP 服务，pending 里出现一项，批准后生效。

a 线：添加一个有 remote 的 git 目录，agent 写出 `.operad/dev.json`，界面列出它选的检查命令；新建一个 flow，加一个 work 阶段和一个 check 阶段，保存成功；删掉所有 check、review、human 阶段再保存，被拒绝并显示原因；用这个 flow 建一个 task，在应用里跟到合并；在文件浏览里打开一个源文件和一个 Markdown 文件。

连远程：填另一台机器的地址和 token，对话和 pending 可用，文件浏览和 serve 的启动停止不显示。

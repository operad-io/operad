# ADR 0026: The Chat

Status: accepted

## Background

operad began as flow-first. A long conversation with an agent that lasts days, moves between devices (a phone and Telegram are the same chat), uses tools, reads and writes a knowledge base and asks a person in the middle is a second way to use it. The chat is an object of a base plugin, not a kernel feature: the kernel gains no conversation concept, no type-level action and no new object kind.

## Decisions

### D1: A chat is one object, and the user's word is "chat"

The user-visible word is chat, never conversation or session (session is each harness's name for its own session, and users would confuse them). It belongs to the `chat` base plugin, installed with operad. Its fields are: parent object, harness, working directory, access profile, skills, title, the harness's session reference (internal, never shown) and the bound channels. A message is a fact on the chat (who, when, text, attachment paths, source reference), not a field. The `chat` plugin knows nothing of repositories or bots: the plugin that creates a chat gives it every field at creation.

### D2: An incoming message is an event, and a default rule replies

A message arrives as an event whose source is `ios`, `telegram` or `cli`, whose `key` is the message id and whose `object` is the chat's id. The `chat` plugin carries default rules that start `chat:reply` with `auto` on that event (the plugin default rules of ADR 0010 D4).

### D3: `chat:reply` is one step and a loop

The step builds the prompt from the unanswered messages found in the chat's facts, never from the event's data, so a message that arrives while a run is going is also seen. It continues the chat's harness session (`resumeSession`), records the reply as a fact, and updates the session reference.

A message that arrives while the reply is being written is handed to an agent whose harness declares `takesMessagesMidRun`, after the tool calls already running; the reply is not interrupted and that message starts no extra round. The reply's `replyTo` names the messages it was given, and an attempt that ends without a reply message records the mid-run messages it took, so one it took is not answered again. A message the agent does not take before the reply ends, and a message with an attachment, waits for the next round as before. Before it ends the step looks again for messages that arrived meanwhile; if there are some it runs again, capped by `maxVisits`. The reply is recorded as a fact before the step counts as done, so a message is never answered twice. A reply that a serve stop, restart or crash cuts off is not rerun: the chat keeps the items it had finished and one line saying it stopped, its messages stay unanswered, and `/retry` continues them; messages that arrived during it wait as after a stop. The length of a chat's context is the harness's concern (the harness compacts); the kernel stores no prompt.

### D4: Sending a message is an action with a `note`

`chat:send <chat> --note <text>` is the one way to send. The app's input box, the command line and the Telegram channel all use it; the client API gets no new call. A message may also carry attachments (ADR 0027 D1).

### D5: A chat is shown through the display interface

The list is `list chat`, with the chat shown under its parent object (a repository or a bot). The chat page is a `transcript` section, live (ADR 0019), refreshed from `events`, plus an input box. A chat has a row state `closed` when closed and `open` otherwise.

### D6: A question in the middle goes through `ctx.ask`

When the agent asks a question or asks for permission in a chat (ACP `request_permission`, radian's `ask_user`, claude's `canUseTool`, pi's `tool_call`), the step uses `ctx.ask` (ADR 0008). The question becomes a pending item whose object is the chat, and any client (the app, Telegram) can answer. An answer inside the grace period continues at once. After the timeout the step ends `waiting`, the process exits, the same item stays pending, and the answer returns to the same step through the harness session. Only a harness that cannot resume refuses once on timeout.

A question the agent asks as a form is a form in the pending item (ADR 0008 D7): the item carries one or more questions, each with its text, a short header, choices with a label and a description, single or multiple, and whether free text is allowed; the person answers each question with a choice, their own text, or by skipping it. Answering sends the answers back to the agent in the shape its harness expects, never as a plain chat message; a chat message is not an answer. Clients that do not know the form keep the pending item's `prompt`, `choices` and `choiceInfo`, and answer a one-question form with a choice as before.

What each harness reports today, and what operad does with it:

- `claude`: `AskUserQuestion` is a tool call that arrives at `canUseTool` with `questions: [{ question, header, options: [{ label, description }], multiSelect }]`. The answer goes back through the permission result's `updatedInput.answers`, keyed by the question's text; a `multiSelect` answer is comma-separated. A skipped question is reported as `annotations[question].unanswered: "skipped"` only to a session whose init line advertises `ask_user_question_unanswered_v1`; any other session gets an empty answer text. The access profile does not judge the tool, because the person's answers are not a permission. This was checked against the user's own `claude` 2.1.327 through the Agent SDK client: the call came to `canUseTool` and the answer sent this way reached the model as the tool's result. Before this decision the profile refused `AskUserQuestion` as a tool it could not check, so a claude chat that asked a question got an error instead of a person.
- `codex`: the app-server sends `item/tool/requestUserInput` with `questions: [{ id, header, question, options: [{ label, description }], isOther, isSecret }]` and reads `{ answers: { <id>: { answers: [<text>] } } }`. `isOther` becomes free text; codex has no multiple choice. A question whose `isSecret` is true is answered empty and never put to the person, so a secret answer is not kept in the pending item or the fact log. `isBlocking` and `autoResolutionMs` do not decide anything here: every other question is put to the person with the usual grace. This was read from `codex app-server generate-json-schema` of the installed codex-cli 0.166.0; it was not run end to end, because a model cannot be scripted to ask.
- `radian`: over `radian acp`, an `ask_user` becomes one `session/request_permission` per question, with one `allow_once` option per question choice (`optionId` `<question>:<choice>`, `name` the label) and a `reject_once` `Decline`; the question is in `toolCall.rawInput`, and a text question fails the tool. This was checked with a real `radian` 0.5.1 `acp` against a scripted model. operad's radian step starts `radian exec` today (ADR 0022 D3 decides `radian acp`; the harness has not moved yet), and there the tool is not offered at all (`ask_user: off (no interactive user)`, checked the same way). Until the radian step speaks ACP, a radian chat's question reaches the person as text in the reply.
- `pi`: 1.5 has no tool a model asks a person with (its tools are `read`, `write`, `edit`, `bash`, `find`, `grep` and `ls`, and its UI prompts belong to extensions), so a pi chat's question is text in the reply too.

A plan review is a form of one question. Its `text` is the plan's title and its `body` is the plan's Markdown; its two choices are `Approve` and `Request changes`. Approve lets the agent's call run, so `claude` leaves plan mode the way it does today. Request changes refuses the call with the person's note as its message and ends the reply, so the person's next message says what to change. It takes the same grace and waiting path as any other question: after the grace the item stays pending, and a late answer reaches the same step through the harness session. An empty plan is refused instead of approved, and a plan holding a secret value is refused without asking.

Only `claude` exposes an equivalent plan call today (`ExitPlanMode`); `codex`, `pi` and `radian` do not, so a plan there remains text in the reply. The user-visible word is Plan; the `dev` plugin's plan object is unchanged.

### D7: Memory is a knowledge base, not the engine

What a bot remembers across chats is written in a Markdown knowledge base, and a skill decides how it is read and written. The engine stores only the chat record. The harness's own memory does not take part.

### D8: Every chat has an access profile

The working directory, the denied directories and the dangerous commands come from the chat's access profile (ADR 0025). A question that a dangerous command raises goes through D6.

### D9: The harness is chosen per chat and never changes

Creating a chat chooses the harness; changing it means creating a new chat (the same rule as a task's flow after work has begun). Each harness's abilities are shown as its plugin describes them: radian has no one-time permission, so in its chats a permission question can only be refused once, and that is said when the chat is created.

### D10: The user says "agent", and the model and effort can change

The user-visible name of the chosen harness is **agent**. The parameter of the creating actions is `agent` (command line `--agent`), its text says agent, and its values are the names of harness plugins (claude, pi, radian). Harness stays a word for plugin authors and code and is not shown on a chat's surface.

A chat's row and page state its agent and, when known, its model and the accumulated cost. The model is a setting of the chat: a new chat uses the agent's configured model, and `chat:model <chat> --model <name>` changes it, effective at the next reply. The agent does not change (D9); the model does. The effort works the same way: a setting of the chat, whose levels each harness plugin lists (claude's effort levels; pi's thinking levels mapped onto them; radian lists none), defaulting to the agent's own, changed with `chat:effort <chat> --effort <level>`, effective at the next reply. The user's words are model and effort (not thinking). The choices are listed by the harness plugins, never written into a client. An agent that lists none offers no such action, and a model or effort the agent cannot take fails the reply with a message naming it, never falling back to another.

### D11: A chat can be closed

`chat:close` asks for confirmation and records a `chat.closed` fact. The row then shows `closed`; `chat:send` is refused with a line saying the chat is closed, no other action is offered, and the transcript stays readable. The list filters are `open` (the default) and `closed`, with the kernel's `all` added after `open`, so a list hides closed chats unless asked.

### D12: The speaker is a name, not "assistant" or "bot"

The transcript labels the model's messages with a speaker name, read each time the transcript is drawn. The `chat` plugin's `speaker` setting defaults to `Operad Bot`. A chat whose parent carries a `speaker` of its own (a bot does) uses that name. The stored role of the message stays `assistant` (the model's role in facts and the harness protocol); it is just not displayed.

### D13: A reply in progress says what it is doing

The transcript's `status` (ADR 0019 D4) uses exactly three user-visible words: **Starting**, **Thinking**, and **Running <tool name>**. Starting begins at the first message still unanswered, before the run and its log exist, and lasts until the log has its ready line. Running names the oldest tool call still going, since its start. Thinking covers every other moment of the reply, since the last line the log received. There is no status while a question waits for the person, after a failure, after a stop, or once every message is answered. A client writes the elapsed part of the line; it is not a new word.

### D14: A failed reply does not poison the next one

A failed reply records its failure line and leaves its messages unanswered, as D3 says. The next reply still gets them, oldest first, each one written as its own message separated by a blank line and `---`. Text that names no command of this chat is a message to the agent and never runs the agent's own command (D4, ADR 0037 D2); a harness hands it over as text, so a leading `/` in a person's message is not parsed as one of the agent's commands.

A reply that ends `done` with no text and no usage, and no error, ended without calling the model. Its failure line says that, with the agent's own reason when it gives one; for claude that is the result's subtype, its errors and a local command the session ran. The line stays one plain line under the limit of ADR 0027 D7.

A message is not sent forever. A reply that fails empty twice in a row for the same oldest unanswered message records that message as taken with the existing `chat.answered` fact, so the next reply starts with the message after it. A failure of another kind, a reply that is not empty, or a different oldest message starts the count again. A rerun of the same attempt is not a second reply.

### D15: A chat has an access level

The level is a setting of the chat, like its model and effort, and belongs to that chat until a person changes it. `chat:access <chat> --level <level>` changes it, the action is offered as `/access`, and a closed chat does not offer it. The argument is one of `plan`, `ask`, `edits` and `full`. A `chat.access` fact records who changed it, from what and to what. Every reply after it uses the level, across restarts and clients.

The plugin that creates a chat gives it its starting level: a bot chat starts at the bot's `accessLevel` setting (`ask` unless the bot sets it), a repository chat at `plan`. A chat on which no one ran `chat:access` follows that setting at its next reply, so changing the setting moves it; a level a person chose stays. The row shows the level when it is not that chat's starting level. Apart from that starting value, the chat plugin knows nothing of bots or repositories; the creating plugin gives the field.

Every reply composes the chat's access profile with its level in `@operad-io/access-match` (ADR 0025 D8), so every harness judges the same asks. A harness that cannot carry a level refuses the reply at its start with a message naming the level; it never ignores it.

The menu's title is `Access` (权限模式). The levels' approved words are `Plan only` (仅规划), `Ask each time` (逐次确认), `Accept edits` (自动接受编辑) and `Full access` (完全访问). The action's information gives each level a short description; `full` carries the risk that it skips every question, leaving only the profile's deny rules, a read-only working directory and a write under `readPaths`.

## Not decided here

Chats are not imported from outside operad (a terminal's Claude Code session, a pi session).

### D16: The chat view says how full the context is

Each finished reply records, beside its usage, the number of tokens in the agent's context at the end of the reply: the last model call's input plus its cache read and cache write, the prompt the model last saw, never the sum over the reply's calls. It also records the model's context window when the agent's model list gives one; an unknown window is left out and is never guessed. A harness that cannot tell the last call's context leaves the number out.

The chat's view carries `context: { used, window?, model }` from the last finished reply of the session in force: `used` is that number, `window` is the model's context window when known, and `model` is the model that answered when known. `GET /v1/objects/<id>` returns it beside the row and the section directory, and the `transcript` section returns it with every read. A client shows the numbers without adding anything up.

A new session resets the view: after `/new`, or after a model change that starts a new session, the view carries no `context` until the next reply. The server adds no user-visible text of its own for it. The clients use the approved words `Context used` and `上下文用量`.

### D17: A chat shows its queued messages and lets a person withdraw or change one

A message is **queued** from when it is sent until a run takes it. A run takes the messages of its first prompt when it starts, and each message an agent takes while the run is going; a message an attempt has taken stays taken, even when that attempt fails and another run answers it. A message with an attachment, or one sent to a run that does not take messages mid-run, stays queued until a run starts with it.

A chat's row carries `data.queued`, the queued messages in sending order, each with its id, text, time and attachments, and `data.queuedCount`; it has neither field when nothing is queued. The `transcript` section carries the same `data` on every read, including one with `after` (ADR 0019 D8). A client shows "N queued" above the composer and offers the two actions on each queued message. The approved words are **Queued** (排队中), **Withdraw** (撤回) and **Edit** (修改).

The message a person sent is never changed in place. `chat:withdraw <chat> --message <id>` records one `chat.message_change` fact of kind `withdraw`; the message leaves the transcript, is never part of a prompt, and one history entry says it was withdrawn. `chat:edit <chat> --message <id> --text <text>` records one of kind `text`; the transcript and the next prompt use the new text, and the attachments stay. The actions are not chat commands. Both refuse a message a run has taken with a line naming it, and a taken message never changes.

Taking a message and withdrawing or changing it take one lock per chat, so the facts order them: a take that comes first makes the action refuse, and a withdrawal or change that comes first makes the run skip the message. A message is never both taken and withdrawn or changed. This is not a queue-versus-steer split: there is no `/steer` (ADR 0037 D9).

### D18: A bot's memory notes ride on the message

A bot chat's prompt carries the bot's `memory/index.md` and `memory/instructions.md` as a note on the message, never in the system prompt, and the chat's refresh step names them and the index's cut limit. The first message of a new harness session, and the first message after the agent compacted the session, carries them whole. Before every other reply each file's whole text is hashed; a file whose hash differs from what this session last saw is attached whole on the next message, and a change this chat's own run wrote is not sent back. A compaction is the reply ending with a smaller context than the previous reply in the same session, or the agent saying that it compacted. A pi chat is compacted by operad after a reply when its context nears the window, and by `/compact` (ADR 0023 D12, ADR 0037 D12); the step's data then says `compacted`, and the notes are sent whole on the next message, after the memory turn that ran before the compaction wrote its changes.

The index is cut at about 8,000 characters, with a line saying it was cut; the memory tidy step keeps the file below that limit. The hashes are fields of the chat object, so a serve restart keeps them, and a chat holds at most the files its refresh step names now. A chat whose refresh step names no notes, such as a repository chat, gets none.

### D19: A long chat has segments the transcript marks and reads from

Each stretch that `/new` or a compaction starts is a segment; the chat's start is the first. A compaction is a `compact` or `compact (automatic)` command line that says it worked (ADR 0037 D12). A segment is named by the sequence of the fact that began it, so it keeps its place as the chat grows. A stretch with no message in it is not a segment, so a `/new` typed twice adds one.

A segment's title is the goal of its `/new` when it had one, cut to one line of at most 80 characters. Otherwise, once the segment has had its first exchange (a person's message and the reply to it), the reply step makes one call to the chat's agent on the model its harness declares for background work, else the chat's own model, with the first question and answer and no tools, and records the title as a `chat.segment_title` fact with its model and cost, which the chat's cost sums like a reply's. A call that cannot be made or fails leaves the first line of the question as the title; either way the segment is named once and never again. The first segment carries the chat's own title and is never named.

The transcript marks the start of every segment but the first with a line `### Segment <n> · <date and time, UTC> · <title>` before its first item, in a page and in a read that continues after a mark. A chat with one segment shows no marker. The section's `data.segments` lists every segment, oldest first (`number`, `at`, `kind` of `first`, `new` or `compact`, `title`, `cursor`), once the chat has two or more.

A read of the transcript may start where a person says: the cursor `segment:<n>`, `date:<YYYY-MM-DD>` (UTC; the first item on or after that day) or `message:<id>`. The page is the usual page, size and `next` included, and `next` continues in the chat from its end. A segment, date or message that does not exist is refused with a message that says which. Searching inside one chat is ADR 0038 D9.

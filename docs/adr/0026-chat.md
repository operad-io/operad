# ADR 0026: The Chat

Status: accepted

## Background

operad began as flow-first. A long conversation with an agent that lasts days, moves between devices (a phone and Telegram are the same chat), uses tools, reads and writes a knowledge base and asks a person in the middle is a second way to use it. The chat is an object of a base plugin, not a kernel feature: the kernel gains no conversation concept, no type-level action and no new object kind.

## Decisions

### D1: A chat is one object, and the user's word is "chat"

The user-visible word is chat, never conversation or session (session is each harness's name for its own session, and users would confuse them). It belongs to the `chat` base plugin, installed with operad. Its fields are: parent object, harness, working directory, access profile, skills, title, the harness's session reference (internal, never shown) and the bound channels. A message is a fact on the chat (who, when, text, attachment paths, source reference), not a field. The `chat` plugin knows nothing of repositories or bots: the plugin that creates a chat gives it every field at creation.

### D2: An incoming message is an event, and a default rule replies

A message arrives as an event whose source is `ios`, `telegram` or `cli`, whose `key` is the message id and whose `object` is the chat's id. The `chat` plugin carries default rules that start `chat:reply` with `auto` on that event (the plugin default rules of ADR 0010 D4).

### D3: `chat:reply` is one step and a loop

The step builds the prompt from the unanswered messages found in the chat's facts, never from the event's data, so a message that arrives while a run is going is also seen. It continues the chat's harness session (`resumeSession`), records the reply as a fact, and updates the session reference. Before it ends it looks again for messages that arrived meanwhile; if there are some it runs again, capped by `maxVisits`. The reply is recorded as a fact before the step counts as done: a step that reruns after `operad serve` restarts sees the reply already there and skips, so a message is never answered twice. The length of a chat's context is the harness's concern (the harness compacts); the kernel stores no prompt.

### D4: Sending a message is an action with a `note`

`chat:send <chat> --note <text>` is the one way to send. The app's input box, the command line and the Telegram channel all use it; the client API gets no new call. A message may also carry attachments (ADR 0027 D1).

### D5: A chat is shown through the display interface

The list is `list chat`, with the chat shown under its parent object (a repository or a bot). The chat page is a `transcript` section, live (ADR 0019), refreshed from `events`, plus an input box. A chat has a row state `closed` when closed and `open` otherwise.

### D6: A question in the middle goes through `ctx.ask`

When the agent asks a question or asks for permission in a chat (ACP `request_permission`, radian's `ask_user`, claude's `canUseTool`, pi's `tool_call`), the step uses `ctx.ask` (ADR 0008). The question becomes a pending item whose object is the chat, and any client (the app, Telegram) can answer. An answer inside the grace period continues at once. After the timeout the step ends `waiting`, the process exits, the same item stays pending, and the answer returns to the same step through the harness session. Only a harness that cannot resume refuses once on timeout.

### D7: Memory is a knowledge base, not the engine

What a bot remembers across chats is written in a Markdown knowledge base, and a skill decides how it is read and written. The engine stores only the chat record. The harness's own memory does not take part.

### D8: Every chat has an access profile

The working directory, the denied directories and the dangerous commands come from the chat's access profile (ADR 0025). A question that a dangerous command raises goes through D6.

### D9: The harness is chosen per chat and never changes

Creating a chat chooses the harness; changing it means creating a new chat (the same rule as a task's flow after work has begun). Each harness's abilities are shown as its plugin describes them: radian has no one-time permission, so in its chats a permission question can only be refused once, and that is said when the chat is created.

### D10: The user says "agent", and the model and effort can change

The user-visible name of the chosen harness is **agent**. The parameter of the creating actions is `agent` (command line `--agent`), its text says agent, and its values are the names of harness plugins (claude, pi, radian). Harness stays a word for plugin authors and code and is not shown on a chat's surface.

A chat's row and page state its agent and, when known, its model and the accumulated cost. The model is a setting of the chat: a new chat uses the agent's configured model, and `chat:model <chat> --model <name>` changes it, effective at the next reply. The agent does not change (D9); the model does. The effort works the same way: a setting of the chat, whose levels each harness plugin lists (claude's effort levels; pi's thinking levels mapped onto them; radian lists none), defaulting to the agent's own, changed with `chat:effort <chat> --effort <level>`, effective at the next reply. The user's words are model and effort (not thinking). The choices are listed by the harness plugins, never written into a client. An agent that lists none offers no such action, and a model or effort the agent cannot take fails the reply with a message naming it, never falling back to another.

### D11: A chat can be closed

`chat:close` asks for confirmation and records a `chat.closed` fact. The row then shows `closed`; `chat:send` is refused with a line saying the chat is closed, no other action is offered, and the transcript stays readable. The list filters are `open` (the default) and `closed`, with the kernel's `all` added after `open`, so a list hides closed chats unless asked.

### D12: The speaker is a name, not "assistant" or "bot"

The transcript labels the model's messages with a speaker name, read each time the transcript is drawn. The `chat` plugin's `speaker` setting defaults to `Operad Bot`. A chat whose parent carries a `speaker` of its own (a bot does) uses that name. The stored role of the message stays `assistant` (the model's role in facts and the harness protocol); it is just not displayed.

## Not decided here

Chats are not imported from outside operad (a terminal's Claude Code session, a pi session).

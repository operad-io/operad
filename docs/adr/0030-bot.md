# ADR 0030: The Bot Plugin

Status: accepted

## Background

The target is not a market position but a few personal scenarios: a long-lived bot that can be talked to from a phone at any time, a personal knowledge base and a daily collection of material. What wins is that the bot really acts with no friction; what is not copied is acting without limits by default (ADR 0025). operad keeps the zero friction without the licence: a sentence describes a need, and an agent writes the flow or plugin.

## Decisions

### D1: The `bot` plugin, and its object is a bot

One plugin, `bot`, whose object is called bot. The only new user word is bot. A bot is a persona and a set of permissions: a main working directory, a default harness, mounted skills (directories with `SKILL.md`, ADR 0011 D2), an access profile (ADR 0025) and a speaker name. A skills entry is one such directory, a directory whose direct subdirectories are skill directories (such as `~/.agents/skills`), or a `.agents` directory (such as `~/.agents`) whose `skills` directory is read that way. Every skill directly inside a listed directory is mounted, including one added after the setting was written, because the setting is read again at every reply. There is one bot by default, named `default`; any number may be configured (for example a read-only one and one that may touch the knowledge base). Bots are written in the `bot` section of `config.json` under `bots` (`bots.default`), as the plugin's `settings` with a JSON Schema (ADR 0010 D1), visible and editable through the settings interface. Each bot is one row in a list and is the parent of its chats (ADR 0028). The plugin name, the settings section, the actions, the directory and every user-visible word use bot only, with no alias.

### D2: The main working directory is `~/.operad/bot/<name>/`

The default bot uses `~/.operad/bot/default/`; any other bot has its own directory, `~/.operad/bot/<name>` when none is given. The directories are siblings under `~/.operad/bot/`, and a bot's directory never contains another bot's. A bot whose settings name its own directory keeps it. The bot's memory lives in `memory/` inside its directory, created when missing. The knowledge base is not part of a bot's directory: all bots share it. The rest of `~/.operad` (the fact log, `secrets`, the token) stays in the default profile's `denyPaths`: the bot's cwd is a subdirectory of the operad home, never the home itself. A bot's access profile lets it read and write its own directory, including its `memory/`, and denies every other bot's directory for reading and writing.

### D3: A bot chat is a chat; a bot reaches repositories through operad's tools

`bot:chat` creates a chat on a bot (ADR 0028 D1); the harness is chosen then and does not change afterwards. Skills and the access profile are read from the bot at every reply, so tightening permissions or adding a skill needs no new chat. The bot touches repositories through operad's MCP tools calling `dev` (look at tasks, open a task) and never changes a repository's files itself. A chat that Telegram opens uses the bot the Telegram plugin's `bot` setting names (ADR 0033 D4).

### D4: Only proposals change a bot

A skill the bot writes or changes (including "save what I just did as a skill") is a pending item, and takes effect only after a person confirms it. The same holds for extending the bot: adding an MCP server, and changing its own settings (speaker, harness, access profile, skill list), are pending items; nothing is done without an answer. The bot's access profile lets it read the skill directories, and denies them for writing together with `config.json`, so a direct write is refused like any denied path and changing a skill stays a proposal. A skill a proposal writes under the bot's directory is mounted like any other once a person approves it. The pending item has the actions `Review`, `approve` and `reject`: `Review` shows what would change (the whole `SKILL.md`, the file list with scripts listed apart and, for a changed skill, the diff; for settings, before and after), `approve` applies it and `reject` leaves everything as it was. An unanswered proposal changes nothing and does not block the chat.

### D5: Which MCP servers a bot mounts is in its settings

The MCP servers a bot may use are written in its settings, and only the listed ones are mounted in its chats. Calls to their tools follow the access profile (ADR 0025), and secrets are injected at the boundary. Tools are not loaded on demand.

### D6: The speaker

A bot's speaker name is how its chats label the model's messages (ADR 0026 D12); without one, the `chat` plugin's setting is used.

### D7: operad never executes a skill's scripts

A script inside a skill is kept, and operad itself never executes it: the bot runs it in its own shell, like any command, under the access profile.

### D8: A bot is created with only the skills and MCP servers chosen

A bot is created by the `bot:create` action on a bot. It takes a name, an agent, optionally a model, an effort and a speaker, and the skills and MCP servers to give the new bot. Skills are chosen from what the home already knows: the skills other bots mount, the skills directly inside a listed directory or `.agents` directory, and the skills in `~/.agents/skills` when it exists; a path may be given instead. MCP servers are chosen from the servers a person already approved on another bot (ADR 0031 D7).

The new bot has exactly what was chosen. No skill, setting or server is inherited from `default`, and a bot that chooses none has none. The name is a bot name (D2), and an existing name is refused. Its page shows its skills by name and its MCP servers. The result opens the new bot and names the secrets a copied server needs before it starts.

### D9: A bot may use the owner's own agent settings

A bot has the boolean setting `useOwnSettings`, titled "Use my own agent settings", off by default. It is changed only as a bot's settings are changed (D4). When it is on, the bot's agent reads the owner's own configuration of that agent. For claude (ADR 0024 D4) that is the owner's settings, instruction files, memory, skills, commands, subagents, plugins and MCP servers; an agent that does not support the switch yet is unchanged. The bot's access profile still has the last word: everything it refuses is judged before any allow rule of the owner's configuration, and operad's tools, the skills the bot lists, the MCP servers the bot lists and its log hooks stay. A skill or MCP server name that both sides define is operad's. The setting names no single agent and covers every agent.

### D10: A bot holds scheduled prompts

The user-visible word is **Scheduled** (Chinese 定时任务). A scheduled prompt
belongs to one bot: a name, a five-field cron schedule in the machine's local
time zone, the prompt, an optional model and effort, and `paused`. It is shown
on the bot's page with its next run and the last run's result and chat id. There
is no scheduled prompt on a repository chat.

The bot plugin is its own source for these entries (ADR 0011 D3). It reads them
from its bot objects at every check, so a client's add, edit, pause, resume or
remove applies at once. This is the smallest way that keeps the kernel small:
the entries change at runtime, while plugin default rules are fixed at load
(ADR 0032 D9), and writing user cron rules would need a reload and would tie the
bot to the cron source. The five-field schedule still means what ADR 0032 D5
says, and a missed run is caught up with the rule of ADR 0032 D11: the latest
planned minute in the last seven days runs once, and older ones are skipped.

When an entry fires the bot opens a new chat under that bot, titled with the
entry's name and the date, and sends the prompt as its first message. The new
chat starts at the access level `full`, whatever the bot's `accessLevel` setting says, so only the profile's deny rules, a
`readOnly` working directory and a write under `readPaths` can stop a call; an
ask rule and an outward write do not ask. A person may change the level with
`/access` afterwards. The message's event source is `bot`, not one of the chat
clients, so the reply is still a background run; at `full` that flag adds no
outward question, while it still does below `full`. A catch-up firing adds one
line to the prompt naming the planned time and how late it runs; an on-time
firing adds none. The reply continues in the usual chat session, and a person
can keep talking in it.

When the reply ends, the bot records a short summary as the entry's last result
and runs the configured notify command with the same `OPERAD_ID`,
`OPERAD_TITLE`, `OPERAD_REASON` and `OPERAD_LINK` a wait uses, where the reason
is the summary. A failed reply records and notifies its failure line instead.
The notify command is run once per firing; a restart between recording the
result and running the command runs it then.

A client's change is the owner's own edit and is not a proposal. The actions are
`schedule-add`, `schedule-edit`, `schedule-pause`, `schedule-resume` and
`schedule-remove` on the bot, reachable from the command line, HTTP and MCP
like any action. The add and edit arguments are `name`, `schedule`, `prompt`,
`model` and `effort`; the other three take `name`.

### D11: A schedule a bot writes in a chat is a proposal

A person may ask a bot in a chat for a recurring prompt ("every morning at 8,
..."). The bot writes it with the `bot` plugin's `schedule` command, which the
chat's agent calls through operad's `command` tool. The command takes the bot,
`add`, `edit` or `remove`, the entry's name, and the fields being given; `add`
needs a five-field cron expression, the same schedule in words and the prompt,
`edit` needs at least one field to change and the schedule in words, and
`remove` takes the name and the schedule in words. The agent supplies both the
cron expression and the words. A bot chat starts with one line telling its agent
that this is how a schedule is proposed (ADR 0028 D8).

The command makes a pending `bot-proposal` and writes no entry, so nothing
fires until a person approves it. `Review` shows the name, the schedule in
words and as cron, the prompt, the model and the effort, and, for an edit or a
remove, the entry before. `approve` adds, changes or removes the entry with the
existing `schedule-add`, `schedule-edit` or `schedule-remove`; `reject` leaves
the bot as it was. A proposal that adds a name already on the bot, or changes
or removes a name it does not have, is refused when it is proposed. A client's
direct change stays the owner's own edit and is not a proposal (D10).

### D12: The memory plugin owns the wiki and a bot's memory

One plugin, `memory`, owns the wiki and the per-bot memory. Its settings (ADR
0010 D1) hold one path: `wikiDir`, the shared knowledge base, whose default is
the home's `wiki`, so `~/.operad/wiki` for the usual home. The directory is
created when missing and made a git repository when it is not one; a directory
that is already a git repository is used as it is, never initialised again and
never restructured, so a person may point it at their own notes library.

Every bot mounts the plugin's `memory` skill while the plugin is enabled. The
skill says what a bot's memory is for, where the memory and the wiki are, that
the bot writes without asking, that rules the bot must obey do not go in memory,
and the layout below. A bot's memory is `memory/` in its working directory (D2),
with `index.md` (bounded, one line per entry), an append-only daily log under
`log/`, topic notes linked from the index, and a separate `instructions.md` for a
person's long-standing instructions.

Which bots may write the wiki is the access profile's business (D1, ADR 0025).
The default profile lets every bot read the wiki. The default bot also writes
it; every other bot reads it unless its settings set `writeWiki`. A bot that may
not write it has the wiki refused for writing and a read path through that deny.

After a bot reply that changed its memory directory or the wiki, the plugin
makes one commit in each repository it changed, naming the bot and the chat in
the message; a reply that changed nothing makes no commit. A bot's memory
directory is a repository of its own unless it is already inside one, in which
case only its own paths are staged and committed.

A note whose frontmatter says `untrusted: true` — content written after the bot
read a web page, mail or a source item — is kept out of `memory/index.md`: the
plugin removes an index line that links to it and the note stays where it was
written. The mark is the bot's, per the skill: operad does not record the
material a run read, so it cannot mark a note itself.

A note's row shows its modification time as `YYYY-MM-DD HH:mm` in the machine's
local time zone, with no time for a zero time and ` (untrusted)` after the time
for a note marked untrusted. The phone and the desktop show the line as the
plugin gives it.

### D13: A bot tidies its memory at night

A bot's memory is checked once a night, at the bot's `tidyTime`, an `HH:MM` in
the machine's local time zone whose default is `03:30`. The bot plugin is its
own source for this, as it is for scheduled prompts (D10); a missed night is
caught up once, not once per missed night, by the rule of ADR 0032 D11. A bot
whose `tidyTime` changes starts from the latest planned time, so no night before
the change is caught up.

The check costs no model call. It asks the memory plugin whether the bot's
memory changed since the last tidy commit and whether `memory/index.md` is over
its limit. When neither holds the night ends with no cost. A completed tidy
makes one commit even when it changed no file, so the next check measures from
it.

When there is work and the bot's `runWithoutAsking` is off, the bot has one
pending card with the counts of the work: how many notes were added or changed,
how many chats need checking, and whether the index is over its limit. Its
actions are `Run` (Chinese 运行) and `Skip` (Chinese 跳过). An unanswered card
stays and never expires; the next night's check updates the same card's counts
instead of making a second. `Skip` closes it until the next check finds work. A
card is only for a decision, so a tidy that is running or finished has none.
When `runWithoutAsking` is on the tidy runs with no card, and only a change or a
failure sends one line through the `notify` command, beside the usual scheduled
prompt's notification. The setting's title is "Run without asking" (Chinese
不询问直接运行) and it is off by default.

The tidy itself is the memory plugin's work: it reads the notes changed since
the last tidy against the chat records of that period, corrects wrong or out of
date notes (the newer fact replaces the older, and the old note stays marked as
replaced, never deleted), and keeps the index under its limit by moving detail
into topic notes. It ends in one memory commit. A rewrite that drops at least a
quarter of the old index entries is void: the old entries are kept and only the
run's additions stay, so the fallback is append only. A tidy does not start
while any chat of the bot is writing a reply; an automatic night waits for the
next check, and a `Run` waits until the chat ends.

The model is the bot's `backgroundModel` setting when written; otherwise the
harness's declared `backgroundModel` (ADR 0022 D12; `claude` is `haiku`); when
neither is declared the bot's own model, else the harness's default.

An automatic run leaves no card. A run started from the card also leaves no
pending item, and sends one line through the `notify` command even when memory
did not change; an automatic run sends its line only when it changed something
or failed. The line names the bot, what changed (the run's files and insertions
and deletions, or "no memory change"), the cost, and that only additions were
kept when the rewrite was voided. It never carries the agent's reply. The run's
full result — the diff summary, the cost and the agent's reply — stays in the
tidy object's own section. A failed run leaves one pending card, because it
needs a decision: its actions are `Run` (运行) and `Skip` (跳过), and its text is
one short line with the reason.

### D14: A bot without a model login is a pending item

A bot whose agent is a loaded harness that declares a login step (ADR 0022 D13)
and that reports it is not signed in gets one standing pending item, about that
bot, whose prompt names the bot and says it is not logged in to a model. The
item offers the bot's actions; its `login` action, titled **Log in** (Chinese
登录), marks the bot and starts the `bot:login` flow on it; the action and
command name stay `login`. The flow has one step, which calls `<agent>/login`
for the agent the bot names or, when it names none, the one loaded harness that
offers login, and writes the returned model to the bot's existing `model`
setting (`bots.<name>.model`); a bot that names no agent also gets that agent,
so its chats and its model belong together. The write is the person's own
change in the login step, not a proposal: no agent proposed it, the person
chose the model, and the item leaves pending because the harness then reports
signed in. A timed-out or cancelled login changes no setting.

The agent's credentials stay the agent's (ADR 0023 D4, 0024 D3); the bot plugin
writes only its own settings.


### D15: Setup Dev turns on `dev` for a repository through a proposal

The user-visible word is **Setup Dev** (Chinese 配置开发流程). `dev` is off in a new home (ADR 0012 D2), so a person's first work on a repository is a bot chat, and Setup Dev is how that chat turns `dev` on. There are two entries and one result.

The entries. The `setup-dev` action on a bot takes the repository's directory as its `path` argument (`operad bot:setup-dev <bot> --path <directory>`; not `repo`, which the command line reads as a repository scope) and opens a new chat on that bot whose first message is the prepared prompt naming the directory; a client puts it on a button (the settings, or the place where `dev` is off). Every bot chat also starts with one line telling its agent that Setup Dev exists, so a person may say it in a sentence and the agent sends the same prompt to itself. The prompt is one text that the `dev` plugin ships as its guide (ADR 0010 D7) and `docs/user/setup-prompt.md` shows; Setup Dev is the first instance of the guide mechanism, and the `bot` plugin owns the entries that deliver any plugin's guide: the `setup` action on a bot (`plugin` and an optional `target` argument; for `dev` the target is the repository's directory), the `bot setup <bot> <plugin> [target]` command an agent calls (it answers the guide's steps for the items the check reports missing), and the chat command `/setup <plugin> [target]`, which sends that guide to the same chat. `setup-dev` stays as the same entries with `dev` and the directory filled in. It has the agent read the repository's CI and scripts, choose and run the checks, choose the agents that are installed, and then propose; it does not write `.operad/dev.json`, register the repository or start anything itself.

Permission. The chat is an ordinary chat at the starting access level (ADR 0026 D15). The agent's reading of the repository and its running of the checks are judged by the bot's access profile and ask once as any other access does (ADR 0025); Setup Dev adds no grant of its own.

The result. The agent calls the `bot` plugin's `setup-dev` command with the bot, the repository's directory and the `dev.json` text on stdin. The command refuses a directory that is not the root of a git work tree with a remote, a directory already registered, and text that is not a JSON object, and otherwise makes a `bot-proposal` of kind `dev` and writes nothing else. Its pending item has the usual `Review`, `approve` and `reject` (D4). `Review` shows the plugins that would be turned on (`dev`, `shell` and `pool`, those that are off), the `dev.json` that would be written, beside the file's present content when there is one, and the repository that would be registered.

`approve` turns the listed plugins on in `config.json`, writes `<repository>/.operad/dev.json` and leaves a request that the repository be registered; `reject` changes nothing. A change of `config.json` reloads `serve` (ADR 0012 D3). The request is a file `<home>/dev-register/<id>.json` with the repository's directory; `dev` reads the directory on every tick, registers each repository as `operad dev repo add` does, and removes the file. A request that cannot be registered stays, and `dev` shows it as a pending item with the reason until it is fixed or removed. A `dev.json` that `dev` finds invalid is shown by its own pending item (ADR 0015 D5), so Setup Dev needs no check of its own. `mcp.actions` is not changed: a lead's `dev` actions are added by hand (ADR 0034 D4).

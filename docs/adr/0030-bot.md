# ADR 0030: The Bot Plugin

Status: accepted

## Background

The target is not a market position but a few personal scenarios: a long-lived bot that can be talked to from a phone at any time, a personal knowledge base and a daily collection of material. What wins is that the bot really acts with no friction; what is not copied is acting without limits by default (ADR 0025). operad keeps the zero friction without the licence: a sentence describes a need, and an agent writes the flow or plugin.

## Decisions

### D1: The `bot` plugin, and its object is a bot

One plugin, `bot`, whose object is called bot. The only new user word is bot. A bot is a persona and a set of permissions: a main working directory, a default harness, mounted skills (directories with `SKILL.md`, ADR 0011 D2), an access profile (ADR 0025) and a speaker name. There is one bot by default, named `default`; any number may be configured (for example a read-only one and one that may touch the knowledge base). Bots are written in the `bot` section of `config.json` under `bots` (`bots.default`), as the plugin's `settings` with a JSON Schema (ADR 0010 D1), visible and editable through the settings interface. Each bot is one row in a list and is the parent of its chats (ADR 0028). The plugin name, the settings section, the actions, the directory and every user-visible word use bot only, with no alias.

### D2: The main working directory is `~/.operad/bot/`

The default bot uses `~/.operad/bot/` directly; any other bot has its own directory, `~/.operad/bot/<name>` when none is given. The knowledge base and the bot's memory live here. The rest of `~/.operad` (the fact log, `secrets`, the token) stays in the default profile's `denyPaths`: the bot's cwd is a subdirectory of the operad home, never the home itself.

### D3: A bot chat is a chat; a bot reaches repositories through operad's tools

`bot:chat` creates a chat on a bot (ADR 0028 D1); the harness is chosen then and does not change afterwards. Skills and the access profile are read from the bot at every reply, so tightening permissions or adding a skill needs no new chat. The bot touches repositories through operad's MCP tools calling `dev` (look at tasks, open a task) and never changes a repository's files itself. A chat that Telegram opens uses the `default` bot.

### D4: Only proposals change a bot

A skill the bot writes or changes (including "save what I just did as a skill") is a pending item, and takes effect only after a person confirms it. The same holds for extending the bot: adding an MCP server, and changing its own settings (speaker, harness, access profile, skill list), are pending items; nothing is done without an answer. The bot's access profile denies the skill directories and `config.json`, so a direct write is refused like any denied path. The pending item has the actions `Review`, `approve` and `reject`: `Review` shows what would change (the whole `SKILL.md`, the file list with scripts listed apart and, for a changed skill, the diff; for settings, before and after), `approve` applies it and `reject` leaves everything as it was. An unanswered proposal changes nothing and does not block the chat. A run nobody started on the spot may make a proposal but never approve one.

### D5: Which MCP servers a bot mounts is in its settings

The MCP servers a bot may use are written in its settings, and only the listed ones are mounted in its chats. Calls to their tools follow the access profile (ADR 0025), and secrets are injected at the boundary. Tools are not loaded on demand.

### D6: The speaker

A bot's speaker name is how its chats label the model's messages (ADR 0026 D12); without one, the `chat` plugin's setting is used.

### D7: operad never executes a skill's scripts

A script inside a skill is kept, and operad itself never executes it: the bot runs it in its own shell, like any command, under the access profile.

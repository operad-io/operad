# ADR 0002: The Kernel Boundary

Status: accepted

## Background

The kernel stays as small as it can. Whatever can be a plugin is a plugin; the kernel does only what a plugin cannot do, or what every plugin would have to repeat. A user of the kernel should meet as few nouns as possible, and a noun that belongs to a plugin should not be known by someone who does not use that plugin.

## Decisions

### D1: The kernel has five things

1. **The event log**: an append-only record of facts, with causality.
2. **Flow execution**: advancing, resuming after a crash, counting a repeated input once, and stopping when the same step crashes again and again.
3. **Four basic steps**: call one step of a plugin, wait for a person, wait for a time or a condition, end.
4. **Plugin loading**: a plugin declares objects, actions, steps, flows, command-line verbs and the schema of its settings; the kernel knows kinds, not names. Reading and writing settings is also here (ADR 0017).
5. **Three views for the outside**: pending, history, running.

Running commands and checks, scheduling (concurrency, dependencies, priority, auto levels), git, workers, review and merging are not in the kernel.

### D2: Storage is a replaceable backend

The kernel defines a log interface and one conformance test, and ships exactly one backend, `sqlite`. The interface and the conformance test stay, so another backend can be added by following them. A plugin or a user cannot reach the storage format. A plugin's objects (for example the `dev` plugin's task and brief) are stored as facts and are read and written through the plugin's commands.

### D3: Few user nouns

The kernel shows a user exactly three words: **flow**, **pending**, **history**. Every other noun belongs to some plugin, and a user who does not use that plugin need not know it. A new user-visible noun needs the owner's agreement. The nouns agreed so far: the `chat` plugin's chat (not "conversation" or "session"); the `bot` plugin's bot and profile (the access profile a bot sets).

### D4: Development is a plugin, `dev`

`dev` is installed by default and can be left unused.

- Its objects are plan, task, brief, rework and follow-up (the task that collects the problems a review did not block on).
- Its actions are confirm, merge, reject, cancel and auto; they appear in pending and are also usable directly on the command line. It also has the chat action on a repository, which opens a chat in that repository.
- `dev` provides the skeleton and the steps of a development flow. The concrete flow is set per project in `.operad/dev.json`. With no setting, the default flow is: worktree, worker, verify, review, wait for a person to merge, merge into main, clean up.
- A completely different development discipline can still be a separate development plugin, written by hand or generated by an agent.
- `dev` deals with the kernel only through the plugin interface. If it needs to bypass the interface, the interface is designed wrong.

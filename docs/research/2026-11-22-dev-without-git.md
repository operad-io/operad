# Where dev assumes git, and what it takes to add a folder without it

Date 2026-11-22. Research only (T-0727); no code changed. Read first: `docs/backlog/operad-dev-steps.md` (the owner's decisions and open questions), `docs/research/2026-11-22-dev-worktree-dependence.md` (same shape; its "branch mode" and task list are used here), ADR 0039 (`workIn`, on `work/T-0716-workin-setting`, not yet on `main`), ADR 0030 D15 (Setup Dev). Line numbers are of this branch, cut from `main` at 9111bcbd, unless a file is marked T-0716.

What the owner decided, in short: a folder without git, or a machine without the git program, can be added and chatted with, and the chat may change files in it. Git is needed only to create a task. Nothing about git is asked before that. operad does not bundle git; the bot walks the user through installing it when a task needs it. At the first task in a folder without git, or in a git folder with no commit, the bot proposes setting up git there: a `.gitignore` first, the list of files for the first commit, one pending item; approval runs `git init` when needed and the first commit; the result is a branch-mode repository without a remote. A subfolder of a git repository is refused in plain words with a way to add the repository root instead.

## Summary

- **Four places refuse a folder that is not a git work tree with a remote**, each with its own text: `addRepository` (`service.ts:517-588`, used by `operad dev repo add`, the `dev:repo-add` action that the desktop and the TUI call, and Setup Dev's register request), Setup Dev's `rootOf` (`packages/bot/src/setup-dev.ts:65-78`), dev's init check (`check.ts:30-62`, which fails for every registered repository without a remote) and the Setup Dev skill (`skills/setup/SKILL.md:15-16`, "if it has none, say so and stop"). Docs repeat the rule in `docs/user/cli.md:380-384`, `dev.md:361`, `setup-prompt.md:17`, `troubleshooting.md:125` and ADR 0030 D15.
- **Nothing in dev checks that the git program exists.** `runOnce` (`git.ts:76-101`) calls `Bun.spawnSync({cmd: ["git", ...]})`; with no `git` on PATH Bun throws `ENOENT: Executable not found in $PATH: "git"` (checked), which no caller catches. It surfaces as a raw message from `addRepository`, as a failed step, or inside a `try` that prints it as a failure. Setup Dev's own `git()` helper (`setup-dev.ts:55-63`) swallows the error, so the refusal says "not the root of a git work tree" when git is simply missing.
- **On macOS the check cannot be "run git and see".** `/usr/bin/git` is a stub that exists on every Mac; without the command line tools running it opens Apple's install dialog. dev runs git in many places that a no-git folder reaches before any task, and one of them is on the chat path: `trackedAgentFiles` (`chat.ts:141-142`, `git ls-files`), called by `dev/chat_settings` at every chat reply. So the first reply in a chat about a folder would open the dialog (or, on Linux and Windows without git, throw). This is the main design constraint; see section 2.
- **The memory plugin already runs git at every serve start, and it is on by default.** `defaultPluginsFor` (`packages/cli/src/defaults.ts:49-51`) enables `memory`; its `start` calls `ensureWiki` (`packages/memory/src/index.ts:86-87`), which runs `git init` on the wiki directory (`memory.ts:150-165`, `memoryGit` at `:117-129`). On a Mac without the tools the dialog opens at the first `operad serve`, before any folder is added; on a machine without git `start` throws. This breaks "nothing about git is asked before a task" regardless of anything dev does. It is outside the brief's list and needs its own task (task 9 below).
- **Views, the scheduler, the settings readers and the settings editor need no change.** The only repository-level git reads in `views.ts` are for one task's diff and the commit link (`views.ts:816`, `:868-871`, `:897-949`); a folder without git has no task, and a task cannot be created in one. `schedule.ts` and `standing.ts` call no git; `settings.ts` and `project-settings.ts` only read and write `.operad/dev.json` (the file is written by `writeSettings`, `service.ts:470`, and works in any folder).
- **A "no git" repository needs no stored field.** What git a folder has changes without operad (the user runs `git init`, installs git, makes a commit). A stored flag would be stale on the next tick. The fact is a function of the folder: `gitStateOf(path)` returning one of `no program`, `no repository`, `subfolder of <root>`, `no commit`, `ready` (section 5). Its answer is used by task creation, by the chat context text and by the setup proposal. What it never needs is a new word.
- **Chat in a no-git folder needs the "chat works in place" work (the first chat task of P-0132).** Today a chat in the main clone is read-only and gets write access only by opening a worktree through git (`chat.ts:557-668`). Without git that path cannot work, so a no-git folder's chat writing files depends on that task, and the no-git folder must never be offered a worktree.
- **The reachable end state is the same repository the branch-mode work builds** (branch mode, one task at a time, no remote). The git setup is therefore useful only after branch mode (T-0718 and its integrate task) and the no-remote task (T-0722) have landed; the chat-only part can land before them.

### What a bot chat and a task started by a chat do

`dev:task` from a repository chat takes the chat's worktree (`chatWorktreeOf`, `chat.ts:333-351`) only if the chat has one; a chat in place has none, so a task is an ordinary task and the refusal of section 6 applies to it as to any other.

## 2. Detecting "git installed" without the macOS dialog

The dialog comes from `/usr/bin/git`, `/usr/bin/python3` and the other stubs of `xcode-select`. They exist on every Mac and, without the tools, run `xcode_select_invoke_tool`, which opens the dialog and exits 1. So on macOS "run `git --version` and see if it works" is the one test that must not be used. Results below are marked checked (on this machine, Xcode installed) or unverified (needs a Mac without the tools, such as a clean VM).

- **Linux:** `Bun.which("git")` (a PATH scan; nothing is run). Then `git --version` may be run to confirm. No dialog exists. A distribution where `git` is a shell function or a "command not found" hook does not matter, since a spawn needs a file.
- **Windows:** `Bun.which("git")` (it honours PATHEXT, so `git.exe`). Unverified here. If it finds nothing, look at the usual places before saying "not installed": `%ProgramFiles%\Git\cmd\git.exe`, `%ProgramFiles(x86)%\Git\cmd\git.exe`, `%LOCALAPPDATA%\Programs\Git\cmd\git.exe`. **PATH goes stale:** a `winget install Git.Git` from the bot changes the user PATH, but the running `serve` still has the old one, so `Bun.which("git")` keeps failing and every `git()` spawn keeps failing with ENOENT until `serve` restarts. The finder must therefore return an absolute path, `git()` must spawn that path and not the word `git`, and a negative answer must not be cached (re-scan on each call or on a short clock). The same holds on macOS with Homebrew into a serve started from the app (GUI apps have a short PATH).
- **macOS:** resolve `git` through PATH without running it (`Bun.which`). If the result is anything but `/usr/bin/git`, it is a real git (Homebrew `/opt/homebrew/bin/git` or `/usr/local/bin/git`, Xcode's own). If it is `/usr/bin/git`, it is real only when `xcode-select -p` exits 0, prints a directory, and `<directory>/usr/bin/git` exists (that is `/Library/Developer/CommandLineTools/usr/bin/git` or `/Applications/Xcode.app/Contents/Developer/usr/bin/git`). `xcode-select -p` only prints the selected developer directory; it does not start the installer (checked here: it printed `/Applications/Xcode.app/Contents/Developer`; the no-tools behaviour, exit 2 with "unable to get active developer directory", is unverified). `DEVELOPER_DIR` in the environment is honoured by both, so the check runs with the same environment as the spawn. When the tools are selected but Xcode's licence is not accepted, `git` exits non-zero without a dialog: after the check passes, a `git --version` is safe and tells "installed but cannot run" apart.
- **Where the finder lives.** Three packages spawn git: `dev` (`git.ts`), `bot` (`setup-dev.ts:55`, plus `ensureRepository` in `tidy.ts:874`) and `memory` (`memory.ts:117`). All three depend on `@operad-io/engine`, which already has `engine/src/platform` (process groups, file locks). A `findGit()` there is platform code, not git knowledge, so "the kernel does not read git" (ADR 0003) is not touched; the alternative is a copy in `dev` and one in `bot`. Which is the owner's/ADR's call; the code suggests `platform`.
- **When it runs.** Never at add time on its own: `addRepository` asks `gitStateOf`, whose first step is `findGit()`. On macOS that costs one `xcode-select -p` only when git resolves to `/usr/bin/git`. The answer for "installed" may be cached for a short time; "not installed" must not be.
- **Install steps for the bot's guide (the bot proposes; each command is an approved pending item).** macOS: `xcode-select --install` opens Apple's dialog for the user to click and then downloads the tools; the bot waits and re-checks with `xcode-select -p`. Homebrew users can run `brew install git`. Windows: `winget install --id Git.Git -e` (then the restart of `serve` above, or the finder's re-scan by absolute path). Linux: the package manager (`apt install git`, `dnf install git`, `pacman -S git`; this needs root, so it is a command for the person to run or a pending item with `sudo`). The install does not touch operad's own files.

## 3. Git present, but no commit yet, and the first commit

What an empty history does to each step (all checked with git 2.53 in scratch folders):

- `git rev-parse HEAD` fails; `headOf` (`git.ts:160`) returns `undefined`; `git status --porcelain` works and lists everything as untracked.
- `git worktree add <path> -b work/x main` fails with `invalid reference: main`; without the start point git infers `--orphan` and makes a branch with no parent (silent, and a wrong base). So the worktree step (`steps.ts:638-724`, the base `<remote>/<main>` at `:644-651`) cannot work.
- `git switch -c work/<id>` on an unborn branch succeeds **and renames the unborn branch**: `main` never comes into being, and the task branch holds the first commit. Branch mode's `prepareBranch` (`git switch -c work/<id> <base>`) would give `fatal: invalid reference` with a base, but a version that omits the base would silently do this. It must refuse before.
- `integrate` (`integrate.ts:299`) and `updateMainClone` (`mainclone.ts:96`) need a main with a commit; with the local-main form of T-0722 a missing `refs/heads/<main>` would show as an empty base.
- The unborn branch is named by git's `init.defaultBranch` (often `master`), while `mainBranch` in `dev.json` defaults to `main` (`DEFAULT_DEV_SETTINGS`, `settings.ts:370`). The two disagree on any machine without the setting.
- `git commit` fails when there is no user name and email ("Author identity unknown") on machines where git cannot guess one. dev never sets an identity: `commitLeft` (`steps.ts:848-858`) ignores the failure of its commit and returns `false`. A machine where the bot has just installed git has no identity. This was not reproduced here (this machine has a global identity).

**Should the first commit be part of "set up git here"?** Yes: a repository with no commit cannot have a task, and the owner's flow already says approval makes the first commit. What the code suggests for how:

1. The proposal's file list must be what is committed. `git add -A` at approval time would also commit what a chat wrote after the list was shown (and a secret that appeared). Commit exactly the approved paths (`git add --pathspec-from-file=- --pathspec-file-nul`, git 2.25 or later), and refuse if the identity is missing.
2. The list can be made **before** `git init`, without writing into the folder: a scratch git directory outside the folder and the proposed `.gitignore` as an exclude file (checked):
   `git --git-dir=<scratch> --work-tree=<folder> ls-files -o --exclude-from=<proposed .gitignore> --exclude-standard`
   lists exactly what `git add` would take, and leaves the folder untouched. (`git ls-files -o` outside any repository fails: `fatal: not a git repository`.) This does need the git program, which is the case at the first task (the bot installs it first).
3. Do not rely on `git init -b <name>` (needs git 2.28; Ubuntu 20.04 has 2.25). `git init` then `git symbolic-ref HEAD refs/heads/<mainBranch>` works while the branch is unborn.
4. For a git folder that already has an unborn branch with a name other than `mainBranch`: set `mainBranch` in `dev.json` to that name (`git symbolic-ref --short HEAD` prints it on an unborn branch) instead of renaming the user's branch.
5. The setup writes `.gitignore` before the commit, and the `.gitignore` is part of the commit. Defaults to propose: dependency directories (`node_modules/`, `.venv/`, `target/`, `vendor/`), build output (`dist/`, `build/`, `.next/`), `.env*`, key files (`*.pem`, `id_rsa*`, `*.key`), OS litter (`.DS_Store`). The bot can add what it sees. A folder with many files (or the user's home, `~/Documents`) must not become a first commit by accident: the pending item carries the count, and the code refuses past a limit (the owner's number) or when the folder is `$HOME` or a filesystem root. A nested git repository inside the folder makes `git add` record a gitlink and print a warning: list those separately.
6. After the commit: run `ensureExcludes` (now that `.git` exists), set `workIn: "branch"`, leave `remote` absent, record nothing else. Because the lock key changes with `.git` (section 1), the setup runs under the repository lock and nothing may create a task until it ends. It is idempotent: if it dies after `git init` and before the commit, the next run finds an unborn repository and goes on from there; a repository that already has a commit has nothing to do. The request file in `<home>/dev-register/` (`register-requests.ts`) is the carrier that already exists: dev reads it on each tick, a failure stays in the file and shows as a pending item. The bot's approval writes the request; dev does the git work, so only dev (which has `git.ts` and the lock) runs git.
7. A git folder that is unborn **and has a remote** (a freshly created empty remote): the first commit exists only locally, and `<remote>/<main>` does not exist until something pushes. A push is an outward action and is not part of this setup. The code suggests that the setup writes no `remote` for it either (branch mode, local main), and that adding the remote later is a separate step.

## 4. A subfolder of a git repository

**Today:** `addRepository` runs `git rev-parse --show-toplevel`, compares it with the folder (`service.ts:525-537`) and throws `"<path>" is not the root of a git work tree`. Setup Dev's `rootOf` does the same (`setup-dev.ts:70-73`). The message does not name the root, and the two paths ask nothing from a client.

**Refusal in plain words with the root (needed now).** The refusal says which repository the folder is in (`git rev-parse --show-toplevel` has it) and what to do: add that folder instead, with the exact command (`operad dev repo add <root>`) and the same words for the `dev:repo-add` action. A desktop or TUI "add the repository root" entry can be the same action with the path from the message; a structured value would be better than parsing text. `DevRefusal` is a plain string (`model.ts:644`), so a client that wants a button needs a small addition (a typed refusal that carries `root`). Size S for the text, S more for the typed refusal. Setup Dev gets the same message from `rootOf`.

**Can a subfolder be chat-only?** Yes, and it is cheap, because chat needs no git. With the state function in place, a `subfolder` state is allowed to register like `no repository` is, and refused at task creation with the same sentence as the add refusal (the root and the command). What changes:
- `addRepository`: no refusal for a subfolder; skip `ensureExcludes` (the exclude file belongs to the enclosing repository, and no worktree is made inside it); `dev.json` is written in the subfolder (it will appear as an untracked file in the enclosing repository: say so in the docs).
- Chat: in place, as for a no-git folder. `git ls-files -z` run in a subfolder lists only that subfolder (`chat.ts:142`), which is what a chat there wants.
- The duplicate checks (`service.ts:561-570`) compare exact paths only. A project at the root and one in a subfolder are two registrations of overlapping folders; two chats writing at once is the same as two chats in one folder. Decide whether to refuse a folder that contains or is inside a registered one (S).
- Size of the chat-only variant on top of the no-git work: S.

**Tasks in a subfolder (not recommended).** Every git call uses `git -C <repository.path>`, and git has two roots (work tree root and folder). What would have to learn about it: the worktree step (`steps.ts:638-724`, `worktreePath` `:87`: the worker's `cwd` is `<worktree>/<relative path>`, the worktree is of the root), `checkoutEntries`/`changedFiles` (`steps.ts:292-310`, `:373`: porcelain paths are relative to the root while the code compares them with the folder), `views.ts:927` (`diff --name-only` is root-relative), the gate worktree and where checks run (`gate.ts:85-150`, `:175`) and where `dev.json` is read, `mainclone.ts:111` (the status test sees the whole repository, so a change in a sibling folder blocks the fast-forward), `lock.ts:41` (two projects in one repository have different lock keys, so nothing serialises them, and in branch mode they share one clone and one branch namespace), the push of `HEAD:refs/heads/<main>` (shared by all). L to XL with the replay and crash cases, and it exists only for a case the owner can serve with "add the root". The code suggests no.

## 5. What `gitStateOf` needs, and where it is used

One function in dev (`git-state.ts`), computed each time, no stored field:

| State | How it is found | Add | Chat | Create a task |
|---|---|---|---|---|
| `no program` | `findGit()` undefined | yes | in place, no git calls | refuse: git is not installed; the bot walks the person through it |
| `no repository` | program found; `rev-parse --show-toplevel` fails | yes | in place | refuse: the bot proposes git here (`.gitignore`, file list, first commit) |
| `subfolder` | the top level is not the folder | refuse with the root (or chat-only) | in place | refuse with the root |
| `no commit` | `rev-parse HEAD` fails | yes | in place | refuse: the bot proposes the first commit (the same proposal, no `git init`) |
| `ready` | has a commit | yes | per `workIn` | allowed (T-0722/branch mode decide the rest) |

Facts it also gives: the unborn branch name, the root for the subfolder message, whether a user name and email are set (the first commit and `commitLeft` need them), whether there is a remote (T-0722). The dev object `repo` does not need a field; its `chat` action's `when` (`chat.ts:417`) is sync and sees stored data only, so keep refusals inside `run`.

**Where doctor and dev's setup check list git.**
- `operad doctor` (`packages/cli/src/doctor.ts`): `DoctorEnv` has no git fact (`:34-45`). Add `git(): Promise<{installed:boolean; version?:string}>` and one line. Owner decision pending: a missing git is not a problem for a person who only chats, and `report.ok` is `checks.every(ok)` (`:193`). The code suggests the line is `ok` with the note ("git is not installed; chats work, creating a task needs it") and no "next" command, because `formatDoctor` prints `next` only for problems (`:197-201`). If it were a problem line, `operad doctor` would exit 1 for the chat-only user.
- dev's check (`check.ts:66-85`): skip repositories that are not `ready`; with T-0722 skip the remote part. It may return a `note` such as "git is not installed: chats work, tasks need it", but it must **not** return it as a missing item: a missing item makes Setup Dev's guide appear as work to do (`registry.ts:1599-1612`), which asks the user about git before any task.
- `dev setup` text in `docs/user/dev.md` and the guide: the install steps (section 2) belong to the bot's guide for the first task.

## 6. Where task creation refuses, in plain words

The choke points: `createPlan` (`commands.ts:214`, used by `dev plan add` and `dev:plan`, `create-actions.ts:152`) because a plan exists to hold tasks and the person's request is "make a task" in the bot's words, and `addTask` (`service.ts:1050`) / `addTaskLocked` (`:1073`; also used by followups, flaky and chat-created tasks), because that is the only place a task object is made. Both call one `assertCanCreateTask(repository)`, which reads `gitStateOf` and throws a `DevRefusal` (`model.ts:644`: one line, no field name) with the state's sentence and the next step. A plan or task refused leaves nothing in the store. The check runs inside the repository lock, so the state seen is the state used.

Suggested sentences (the owner's words may differ; the bot turns each into the user's language):

- no program: "Creating a task needs git, and git is not installed on this machine. Ask the bot to help you install it."
- no repository: "This folder is not under git yet, and a task needs it. Ask the bot to set up git here: it will show you a list of the files first."
- no commit: "Git is set up here but has no commit yet, and a task needs one. Ask the bot to make the first commit: it will show you a list of the files first."
- subfolder: "This folder is inside the git repository at <root>. Add <root> as the project instead (`operad dev repo add <root>`), or keep chatting here."

The worktree step gets the same precondition (`steps.ts:901`, before `prepareWorktree`) so a task whose repository lost its git fails with the same sentence instead of git's text. The bot's guide (skill) reads the sentence and starts the setup proposal; the refusal itself never starts anything (nothing is asked before a task).

## What the code suggests for each open question

- **A state or field for "no git"?** No stored field. A derived `gitStateOf` (section 5). A stored value would be stale after the user's own `git init`, after the install, or after a first commit made outside operad. What is stored is only `dev.json` with `workIn: "branch"` and no `remote`, which is the same file a repository with git gets.
- **Does the chat need `workIn: "branch"` in a no-git folder, or a special case?** Write the setting at add. The chat then works in place by the same rule as any branch-mode repository, and a no-git folder with `workIn: "worktree"` (a hand-written file) is still protected by the refusal in `runChatAccess`. One rule plus a guard is smaller than two rules.
- **Detecting git.** Section 2: PATH scan without running anything; on macOS the stub is trusted only when `xcode-select -p` says the tools are there; never cache "no". The Windows PATH after a `winget` install is the case that will bite: spawn by absolute path.
- **No commit yet.** The first commit belongs to the setup; the worktree and branch steps refuse earlier with a sentence, because git's own answers on an unborn branch are either an error or a silently wrong base (section 3).
- **Branch name.** Take the unborn branch's own name as `mainBranch` rather than renaming; when `dev` runs `git init` itself, use `symbolic-ref` to the `mainBranch` value.
- **Identity.** Check `user.name` and `user.email` before the first commit and say so; the sentence needs the owner's answer on what to use when none is set (ask for a name and email in the pending item, or commit with a fixed operad identity for this one commit). The code cannot decide that: it is personal information, and `commitLeft` today fails silently when it is missing.
- **Subfolder.** Refuse with the root named (S). Chat-only is a small addition (S, task 8) and the code has no reason against it; tasks in a subfolder touch the lock, the status test, the diff, the worker path and the gate (L to XL) for a case "add the root" already serves.
- **Who runs the git setup.** Dev, through the request file the bot's approval writes (as Setup Dev does for registering), so the failure path and the lock are dev's. The bot only proposes.
- **Where the first-commit list comes from.** A scratch git directory outside the folder (section 3): the list is exact, and nothing is written into the folder before approval.
- **A folder that is the user's home or a very large tree.** Needs a limit; the code cannot choose the number.
- **Memory.** Not in the brief, but required for the claim; see task 9.

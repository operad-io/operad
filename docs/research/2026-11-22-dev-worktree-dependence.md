# Where dev depends on a task having its own worktree

Date 2026-11-22. Research only (T-0713); no code changed. Read first: `docs/backlog/operad-dev-steps.md` (owner decisions 1 to 4, open questions 2 to 7), ADR 0020 D3, D4, D9 and ADR 0028 D1 to D3. Line numbers are of `main` at a6cbcab0.

"Branch mode" below is `workIn: "branch"`: the task's branch `work/<id>` is checked out in the main clone, concurrency 1. "Worktree mode" is today.

## Summary

- Three things carry most of the work: the worktree step (`steps.ts:638`, `steps.ts:901`), integrate with the main-clone update (`integrate.ts:299`, `mainclone.ts:96`) and the cleanup hooks (`settings.ts:349`). Each assumes that the branch is not checked out in the main clone and that the main clone stays on `main`.
- Three things need almost nothing: verify, review and the report path. They check a commit in a detached gate worktree (`gate.ts:85`, `gate.ts:119`) that does not depend on the task's worktree. **The gate worktree can stay in branch mode.** Only the backlog's wording "checks run in the main clone against the work area" is a different design; see question 5.
- The check "changed the main checkout" is switched off by its own path test in branch mode (`steps.ts:338`), but its message and the review prompt then lie unless they are gated on the mode.
- Every step assumes a remote: `fetch`, `<remote>/<main>` as the base, a push of the task branch, a push of main. A repository with no remote fails at the first fetch of the worktree step (`steps.ts:644`) and is already refused when it is added (`check.ts:36-62`). Branch mode is not what makes that hard; "merge without push" is a separate cross-cutting task (task 7 below).
- The scheduler already refuses a second task over the repository cap (`schedule.ts:921`), but only `running` and `review` tasks hold a slot (`schedule.ts:82`). A task waiting for a person holds none, and in branch mode it still has the clone. This needs a change.
- `readDevSettings` reads `.operad/dev.json` from the main clone's working tree (`settings.ts:1662`, about 15 call sites). `dev.json` is committed. With a task branch checked out the file is the branch's version.

## 3. The gate worktree and where checks run

- `gate.ts:85-93` `gateWorktreePath`: `<worktreeRoot>/<id>-gate`. `gate.ts:119-150` `recreateGateWorktree`: removes whatever is there and `git worktree add --detach <path> <sha>`. It is used by verify (`gate.ts:260`), review (`gate.ts:2152`) and integrate (`integrate.ts:606`, `:897`).
- Verify (`gate.ts:175`) runs the check commands with `cwd: path`, the gate worktree, against the commit `branchHead` returns. It never uses the task's worktree, so **it does not change in branch mode**, as long as the work is committed before verify (the worker commits, or `flowCommit` makes dev commit; for branch mode the second should be the default, see section 2).
- A detached worktree of a commit does not conflict with the branch being checked out in the clone (git refuses the same branch in two worktrees, not a detached HEAD).
- `settings.ts:349-352` cleanup removes `$OPERAD_WORKTREE-gate`, so cleanup of the gate needs no change.

What changes is only a choice: the backlog (item 2, point 3) says checks run in the main clone against the work area. The code would let them run unchanged against the commit in the gate worktree, which also means "the checks pass, then dev commits" is "dev commits, then the checks run, and a failed check leaves a commit on the task branch". That is harmless (the branch is the task's), and it is what the backlog's acceptance line "test that fails leaves no new commit" would contradict. See question 5.

## 4. Where the reviewer's report is written

- `gate.ts:1283-1296` `workspaceReportPath`: `<gate worktree>/.operad/review/<run>-attempt-<n>-review-<round>-try-<k>.json`, created by `prepareReportFolder` (`gate.ts:1304`, plain directories, never through a link). `gate.ts:2116-2150` copies a pending report out of the old gate worktree before `recreateGateWorktree` replaces it (crash recovery). Reports are then copied to the store (`ctx.store.root/dev/reviews/...`).
- Everything is under the gate worktree, so **nothing writes a report into the user's folder in branch mode** as long as the gate worktree stays. The backlog's point 4 ("要定写到哪") has a default answer in the code: the same place. If the owner wants no gate worktree at all (question 5), the report path moves to the store (`ctx.store.root/dev/reviews/<run>/`, already used for the copy) and the reviewer's access profile must allow writing there; that is a small change but a real one.

## 5. "Changed the main checkout"

- `steps.ts:1766` takes `checkoutSnapshot(repository.path)` before the worker; `steps.ts:1784` `newCheckoutChanges` compares after, leaving out paths inside the task's worktree (`steps.ts:338-347` `insideWorktree`); `steps.ts:1843-1846` adds `changed the main checkout: <paths>` to the step's message and the worker's answer.
- `gate.ts:717-737` `mainCheckoutChanges` reads that line back from `attempt.finalMessage`; `gate.ts:739-767` adds one `major` finding per path ("the work changed this file in the main checkout"); `gate.ts:951-957` tells the reviewer the same; `gate.ts:1920` passes it into the round.
- In branch mode `relative(checkout, worktree)` is `""`, so `insideWorktree` returns true for every path (`steps.ts:340`) and no change is ever reported. It is off by accident. It should be off on purpose: skip taking the snapshot, and keep the line from `gate.ts:951` out of the prompt. Nothing else changes; an old attempt's `finalMessage` that still has the line (a task switched from worktree to branch) would still produce the findings, which is right.

## 6. Integrate, the merge, push and the main clone

- `integrate.ts:299` `runIntegrate`. Base is the remote's main: `refs/remotes/<remote>/<main>` (`:324`), after `git fetch --prune <remote>` in every round (`:466`, `:543`, `:570`, `:602`, `:886`). The candidate is built in the gate worktree (`recreateGateWorktree` at `:897`, `mergeCandidate` `:131-170` merge or squash of the verified sha) and **pushed from the gate worktree**: `git push <remote> HEAD:refs/heads/<main>` (`:768-775` batch, `:1158-1165` single), after the outward-action guard `pushAllowed` (`:352-373`). A replay after the push decides by fetching and checking the candidate is an ancestor of remote main (`:455-500`).
- Then `followMain` (`integrate.ts:91-106`) → `updateMainClone` (`mainclone.ts:96-148`) brings the main clone to the commit: it refuses unless the clone is on `<main>` (`:102-108`, note `the main clone is on "x", not "main"`) and clean (`:109-117`, note `uncommitted changes`), and then runs `git merge --ff-only <sha>` (`:132`). A refusal is only a note on the task (`mainCloneChange`, `mainclone.ts:84`), never a failure: the merge is already on the remote.
- Needs in branch mode:
  1. **Switch back before the fast-forward.** At integrate time the clone is on `work/<id>` and the tree is clean (the work was committed). `updateMainClone` as written would say "not main" and never move the clone. Branch mode must `git switch <startingBranch>` first (the record from section 1), then fast-forward. If the person was meanwhile on another branch or has uncommitted changes, the existing notes are the right behaviour; the task is merged either way, and the clone stays on the task branch, which must then be named in the note.
  2. The merge itself (candidate in the gate worktree, push) needs no change.
  3. No-remote repositories: not supported anywhere (see summary). The minimal form is: base = local `<main>`; candidate built in the gate worktree as today; instead of `git push`, advance local `<main>` (`git update-ref` with the old value check, or switch and `merge --ff-only` in the clone); no `fetch`, no `<remote>/` refs, no task-branch push (`steps.ts:2131`), no remote branch deletion in the hook (`settings.ts:354`), `gate.ts:104` and `:2090` use the local branch. About 25 places name `settings.remote` (grep `settings.remote` in `steps.ts`, `gate.ts`, `integrate.ts`, `check.ts`, `views.ts:890`). The setting `remote` would need an "absent" value; that is a schema change (`dev.schema.json`) and a new meaning, so it is the owner's call (the backlog's `operad-desktop.md` item 4 already decided "no remote can be added, merge does not push").
- `integration-queue.ts` (544 lines) serialises tasks that integrate at once and batches them; with concurrency 1 it has only one member. No change, no use.

## 7. Rework, reject, cancel and branch cleanup

- Rework and reject: edges back to `worktree` (section 1); the branch keeps its commits. Reject does not discard work today. The backlog (item 2, point 6) says reject in branch mode "returns the work area to how it was"; that is a new behaviour (switch back to the starting branch and keep or delete `work/<id>`), not a port of a worktree behaviour. In the code today "reject" means "send it back to its worker" (`docs/user/dev.md:420`).
- `cancelTask` (`service.ts:2002-2050`) and `pauseTask` (`service.ts:2057`): write the phase, withdraw a queued integration, cancel the run. **Nothing removes a worktree or a branch on cancel**; the only cleanup is the after-merge hook list `DEFAULT_AFTER_MERGE` (`settings.ts:349-355`, run by `runCleanup`, `integrate.ts:1204-1290`, with `OPERAD_WORKTREE`, `OPERAD_TASK`, `OPERAD_REMOTE`). So "the task branch stays after cancel" (open question 3) is what happens today; it needs no code.
- Branch mode needs: on cancel or reject-to-stop, if the clone is on `work/<id>`, switch back to the starting branch when the tree is clean, and say so when it is not (a cancelled worker may have left edits: they stay in the work area; dev must not discard them, since the user's files may be mixed in). Cancel runs from `service.ts` under `withRepoLock` with no run to do git work in, so this is a new place to put git calls (a step in the cancel path, or on the next `worktree` or integrate of another task: question 4 below).
- Cleanup defaults in branch mode: the two worktree removals are guarded by `-e` (`settings.ts:350-351`) and do nothing; `git branch -D work/<id>` (`:353`) fails if the branch is still checked out in the clone, so the switch back must come before cleanup (it does, from section 6); the remote branch delete (`:354`) is as today.
- `pauseTask` "keeps its branch, worktree" (`service.ts:2058`) and "holds no concurrency slot": in branch mode a paused task whose branch is checked out holds the clone. See section 8.

## 8. The pool's concurrency and how a second task would be refused

- `schedule.ts:909-925` `canStart`: a ready task starts only if `repositoryActive < repositoryConcurrency(settings)` (`:921`) and its pool has room (`:923`). `schedule.ts:1130-1165` writes the note on the task: `waiting for the repository's slot (<task>)` (`:1161`) or the pool's. `repositoryTaskCap` and `runningTaskCap` (`settings.ts:1115-1129`) are derived from the pools' worker counts, capped by `concurrency` only when the file writes it (`settings.ts:299-304`, `:372-373`). The default is one worker, so a repository with no `workers` already has the cap 1.
- So refusal of a second task is mostly present: with `workIn: "branch"`, `repositoryTaskCap` returns 1 whatever the workers say, and the existing note is the explanation. The backlog's "setting `concurrency` to 2 or more while in the main clone is refused with what to change first" is a **load-time check** in `settings.ts` (where `concurrency` is parsed, `:1334-1353`, and pools at `:1056-1100`): refuse `workIn: "branch"` together with `concurrency` > 1, or with a pool whose workers add up to more than 1, saying which to change. It also belongs in the settings editor's `settingsValueProblem` (`settings.ts:1673`) so a save is refused.
- **Gap:** `isActive` is `running` or `review` (`schedule.ts:82-84`). A task in `waiting` (needs a person, including "ready to merge") holds no slot and the scheduler starts the next ready task. In worktree mode that is by design (a waiting task costs nothing); in branch mode the waiting task's branch is still checked out in the clone and a second task's start would refuse on the dirty or foreign branch (section 1) or, worse, switch the branch under the first. Options: in branch mode count `waiting`, `ready to merge` and paused as holding the slot (simple; one task at a time until it is merged, cancelled or rejected away), or switch back to the starting branch whenever a task goes to a person (then the clone is free but every return needs a switch and a clean tree). The first matches "step 3, one at a time" and the backlog's "一次一个任务已经由并发 1 保证", which is not yet true for waiting tasks.
- Plans: `planConcurrency` (`schedule.ts:443`, per plan, default 1) and the area rule (`:918`) stay.
- The chat is not counted in any slot (see section 9).

The ADR 0028 D3 wording to change: "A repository chat is read-only in the main clone" becomes a rule for a repository that works in a worktree; in place the chat works at its access level in the main clone, and the worktree offer does not exist.

**Mutual exclusion in the main clone.** Nothing stops a chat reply with write access from running while a task's `work` runs in the same directory. `withRepoLock` (`service.ts:104`, `lock.ts`) serialises dev's own store writes, not a harness process. What exists to build on: `chat_settings` is evaluated at each reply, so it can say "read-only" for a reply while a task is `running`, `review` or holds the clone (question 4); the work step knows the chat replies by object. A reply that is already running when a task starts is not covered by a per-reply check; the task's worktree step must either refuse while a write-capable reply is live or accept it as in backlog point 9.

## 10. Main-clone updates ("uncommitted changes")

- `mainclone.ts:109-117`: any `git status --porcelain --untracked-files=normal` output stops the fast-forward with `uncommitted changes`. In worktree mode this is how a user's own edits in the main clone are protected; the task is still merged and the clone is just behind.
- In place the clone is always the work area. After a successful branch-mode integrate the tree is clean by construction (everything was committed and verified), so the fast-forward goes through; a dirty tree means the person (or a chat reply) edited meanwhile: the note stays as is.
- `runPrepare` after a fast-forward (`mainclone.ts:50-65`) runs the `prepare` lines in the main clone, as today. The worktree step also runs them in the work area at every attempt start (`withPrepare`, `steps.ts:396`, called at `:969` and `:1068`; the gate runs them in its own worktree, `gate.ts:267`, `:2173`). In branch mode the first run is in the user's clone, on the task branch: a prepare line that rewrites tracked files (a lockfile) would dirty the tree the clean-start rule just guaranteed. State it in the docs; a prepare that changes tracked files is already wrong for the gate.

## 11. Anything that reads `.operad/dev.json` from main

`readDevSettings(repository.path)` reads `<main clone>/.operad/dev.json` from disk each time (`settings.ts:1662`; callers: `steps.ts` 2, `schedule.ts:370`, `:756`, `retry.ts:153`, `standing.ts:47`, `chat.ts` 3, `commands.ts` 2, `views.ts` 3, `project-settings.ts` 1, `check.ts:30`). The review grading file `.operad/review.json` is read the same way (`gate.ts:850`).

In worktree mode a task's own edit to `dev.json` is invisible until it merges and the clone fast-forwards. In branch mode the file in the clone **is** the task branch's version while the task runs:

1. A task that edits `dev.json` changes the live settings for the scheduler, the gate, the chat and views at once, before any check or review. A mistake in it makes `readDevSettings` throw; `runWork` has a path for that (`steps.ts:1368-1389`, `settingsUnreadable`) but `schedule.ts:756` and `views.ts` would show an unreadable repository.
2. `worktreeRoot` or `workIn` itself changed on the branch changes where steps look.
3. The gate worktree and the settings editor (`settings.ts` writes `dev.json` in the main clone, `project-settings.ts`) write into the clone's work area: a settings save during a task puts an uncommitted change into the task's tree (it is then "the worker's change").

The fix is small and has two parts: read the settings once at the start of an attempt and record it (or read it from the starting branch's commit: `git show <start>:.operad/dev.json`), and have the settings editor refuse or defer a save while a task holds the clone. Which one is a design choice; the first is the smaller.

## Questions for the owner (backlog items 2 to 7) and what the code suggests

2. **Dirty start of an in-place task.** Code suggests refuse, with the reason and the files. Without it `changedFiles` (`steps.ts:373`) cannot tell the worker's edits from the user's, `commitLeft` commits both, `mergeLatest` (`steps.ts:593`) fails, and `updateMainClone` refuses to move. A "start anyway" would need a recorded baseline of every dirty path and its hash (the same shape as `checkoutSnapshot`, `steps.ts:330`), and still would not stop `git add -A`.
3. **Branch of a rejected or cancelled in-place task.** Keep (suggested). It is today's behaviour (nothing deletes on cancel, section 7), and the only real cost is the switch back and `branch -D` order, not the choice.
4. **Chat while a task holds the clone.** Suggest: the reply is read-only (a plan-like reply) while a task is `running`, `review`, waiting or paused with the branch checked out, and says why. `dev/chat_settings` already runs per reply and can compute this (`chat.ts:486-540`). Queueing a reply is not offered by the chat package; adding it is larger. A reply that was already writing when the task starts is the one gap.
5. **Review in the in-place default flow.** The code does not make review cheaper in place: it reviews a commit in the gate worktree, as before, and costs only the reviewer's model. The question is therefore the owner's product choice, not an engineering one. What the code does constrain: if the owner wants "no gate worktree at all" (checks in the clone), verify, review and integrate all change (sections 3, 4, 6), which is the largest option. Suggest keeping the gate worktree in both modes. Then "no review in step 2" is just a flow without a `review` stage; the hard rule ("at least one test, review or human stage", ADR 0020 D4) is still satisfied by `test`.
6. **Start of a new repository.** Not a code question; two constraints: `Setup Dev` (`check.ts:30-62`) requires a reachable remote and a main branch on it, so step 1 for a repository with no remote needs task 7 first. The scheduler and `dev:chat` need nothing else.
7. **Does the in-place chat open a branch.** Suggest no. `work/chat-<id>` is tied to the worktree (`chatWorktreeName`, `chat.ts:267`) and nothing else needs it; a chat is the person's own working session in their folder. The clean-tree rule of question 2 is what protects a task that starts after it. A task still opens its own branch (decision 3).

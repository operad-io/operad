# Linger：一个本地个人 agent 产品，以及和 operad bot 的对照（2026-11-19）

读的是 `github.com/simplexai-labs/linger` 在提交 `307f2ab`（2026-11-19）的 README、`docs/` 下的文档、各级 `AGENTS.md` 和审批策略文件。没有安装运行，没有逐行读实现。事实和判断分开写：前六节是事实，标 **厂商** 的出自它自己的仓库和文档，标 **未核** 的没找到可复现的出处；最后两节是判断，都还不是决定。

## 一览

- **定位（厂商）**：SimplexAI（官网 lev8.com）的"本地个人 agent"。读邮件、日历、Slack，记进 wiki，主动提醒，能操作桌面和浏览器。README 自称 "The Grok Bot experience on your PC"。是个人助理产品，不是编码编排。
- **热度**：2026-11-10 公开；九天后 590 star、36 fork、469 个提交，桌面版发到 v0.1.3。
- **规模**：Go 约 26 万行（另有 17.7 万行测试），TypeScript 约 28 万行。九天的公开历史撑不起这个体量，应是内部开发很久后才开源。
- **许可证**：改过的 Apache 2.0。不许对组织外的人提供托管服务，不许去掉前端的 logo 和版权信息；贡献者须同意厂商可以把协议改严或改松。

## 架构（厂商）

| 部分 | 技术 | 职责 |
|---|---|---|
| TeamHub | Go、Gin、PostgreSQL 17、River 队列 | 账号、Room、任务、权限等全部持久状态 |
| node-services | Node 26、Hono、Hocuspocus 和 Yjs | Agent Service、记忆、LLM Wiki、文档协作、语音 |
| Computer Daemon | Go、SQLite | 每台电脑一个常驻进程，启动并监管 runtime |
| teamhub CLI | TypeScript | 155 条命令，agent 靠它操作 Room 和外部应用 |
| Web、Desktop | React 19、Vite | 界面 |

- **不自己写 agent loop**：直接驱动 Claude Code（stream-json）、Codex（app-server）和 Pi（RPC）。模型来源三选一：本地模型（只走 Pi）、订阅（Claude Code 或 Codex）、自带 key。
- **Daemon 只向外拨一条 WebSocket**，本机不开网络端口。每个事件先写进 SQLite 账本再发送，重连后重放。每个 Context（一个 agent 在一个 Room、Task 或文档里）一条有序的命令队列，同时最多 8 个 Context。
- **一个 CLI 代替各工具的 MCP 服务**：帮助、`--schema` 和权限清单从同一份命令定义生成。56 条是自己的命令，99 条是经 Composio 的连接器（Gmail、Outlook、Slack、Notion 等），应用的 key 在 Composio 手里。每次写带 operation ID，重试返回已存的结果，结果不明时只上报、不重发。
- **输入的车道**：屏幕一条，每个 agent 的浏览器各一条。每次输入先记日志再执行，结果不明的输入堵住它的车道，不重放。
- **审批是两层**：先规则，再由一个模型逐个动作评审；策略文件（`apps/teamhub/internal/permissionreview/policy.md`）改编自 Codex。只有服务端验证过的、来自 agent 主人的消息算授权；别的成员、别的 agent、工具输出、网页和文件内容都只是证据。准备动作（打字、填表、存草稿）按它自己的效果判，真正发出去的那一下再判。用户保存的 routine 算主人当场提出，agent 自己建的 routine 不算。**Pi 不经过评审。**
- **服务端并不轻**：Docker Compose 要 PostgreSQL、LiveKit，虚拟机至少 5 GiB 内存。连接器走 Composio，语音识别走 Soniox，这两项是云服务。

## 记忆和 wiki（厂商）

两层：一份个人 wiki，替这个人干活的每个 agent 都能搜；每个 agent 自己的记忆，跨 Room，不跨 agent。

- **wiki 是带类型的 Markdown 页**：客户、联系人、项目、主题各按现实里的实体一页，每次会议一页 Session，链到它涉及的实体。
- **更新是逐节提议、程序核对**：模型读新的对话或文件，按节提出修改，程序把每条修改对着被替换的页面核对。
  - 摘要节要么原样保留，要么改写并给出理由。
  - 列表节一次改一条，按程序分配的 ID，没提到的条目原样不动。
  - 事实要引用它出自哪条消息或哪个文件版本；改写必须保留旧文本引用的每个来源，否则说明为什么丢掉。
  - Change Log 由程序写，不由模型写。
  - 上限：摘要节 3000 字符；列表 20 条、每条 500 字符，超了由模型把最旧的合并成一条带日期的；Change Log 留最新 20 行。
- **搜索只用关键词**：PostgreSQL 全文检索，没有向量和重排模型。一次搜索返回两个分开排序的列表：wiki 页（看全貌）和原始消息、转录、文档、邮件（查细节）。agent 可以带最多六种换说法（同义词、翻译）。说"没记过"之前必须先搜原始记录。记忆里会变的东西（日期、角色、金额）在说成现状之前要对着最新来源核一遍。
- **agent 记忆分三步**：每 5 次成功的运行抽取一次（一份会话摘要加候选记忆）；空闲 6 小时或上下文压缩时合并（去重、去掉被推翻的事实），整份重写；新会话的第一条消息和压缩后的第一条消息带上摘要索引，其余按需读。产物是工作区里只读的 `agent-memory/`：`summary.md`、按主题的 `MEMORY.md`、每个会话一个摘要文件。摘要作为消息上的隐藏附注带进去，不进系统提示，所以新记忆不让提示缓存失效。
- **记什么**：偏好、验证过的做法、决定、环境的事实、失败的教训。不记进度、泛泛的建议、密钥和猜测。
- **LoCoMo 95%（未核）**：只有 README 里一张对比图，没找到评测脚本。部分代码和提示词改编自 Hindsight（MIT），NOTICE 里写明了。

## 主动提醒（厂商）

- **输入**：和 Another Me 的聊天按 20 条一个窗口；Gmail、Outlook 收件箱、Google Calendar 的变动和 Slack 的提及，每 10 分钟轮询一次。
- **每个窗口或事件一次独立的运行**，读通用规则、用户的已学规则和未结的跟进项，结果是四种之一：现在说、先准备再说、以后跟进、不说。
- **节流**：22:00 到 08:00，或当天已经提醒过五次，应用事件只记录；一件事在一个状态下一天只判一次；等聊天安静 3 分钟再送。
- **学规则**：每晚一个模型读它主动发的每条消息和之后的 20 条回复。一句"这种应该早点告诉我"是线索，同类线索出现两次变成规则；用户直接说出种类（"以后这类直接告诉我"）一次就是规则。"太晚了"只会变成那个时段以后跟进，不会直接变成不说。线索不参与判断，只有规则参与。

## 任务委派、团队和模型调度（厂商）

- **任务委派**：聊天里的 agent 叫 Meta，每个后台任务一个 AlterEgo，每个 agent 最多同时 10 个。
  - AlterEgo 不读聊天，brief 带上它需要的；它从不问用户，问题写进报告，由 Meta 决定问不问。
  - 审批卡在等的时候任务是 `waiting_for_approval`，10 分钟过期。
  - 取消是暂停：文件和会话都留着，Meta 可以接着做。
  - 产出写到 Meta 的 `playground/<task-id>/`；一个任务能读同一个 Room 里别的任务的目录，所以前一个任务的输出路径可以原样写进下一个的 brief。
- **`team.md`**：一个 agent 发布一份团队协议（目标、谁主导、每人的部分、谁交给谁）。服务端只在每个 ID 都是这个 Room 里的 agent 时才保存，然后通知文件里点到的每个成员；每次发布整份替换并再通知一次。它是一份给 agent 读的文档，不是可执行的图。
- **模型调度**：每个端点（一台电脑上的一个 runtime）一个队列。
  - 并发数自适应：响应没变慢就加一，明显变慢就减一，被限流或超时就减半并停一分钟不加。速度按每千个新提示 token 比较，长提示不被当成忙。退下来的那个数五分钟内不再试，再失败就把等待翻倍，最多半小时。
  - 七级优先级，从高到低：工具审批、录音问答、聊天、任务和文档、定时和主动、压缩、后台（记忆、wiki）。最后一个名额留给交互类。
  - 聊天及以上排到队首却起不来时，把它下面优先级最低的换出去。被换出的运行保留 ID、状态和会话，轮到时在同一个会话里继续，不算一次失败。
  - 超时只算运行时间，排队不算。

## 本地模型的宣传要打折看

- **"125B 模型跑在 12 GB 显卡"**：靠自家的 MoE 推理引擎 PolyStrata，把最常用的专家放在显存、其余放内存或 SSD。文档自己写明多数速度是模拟档位测的（96 GB 的卡限到 12 GB 的预算）；12 GB 那一档在 62K 提示之后首 token 约 3 分钟，而且那个模型不是这一档的默认推荐。
- **"≈ Claude Opus 4.6"**：依据是自家的 SimplexAI 分数，挂在第三方的 AIHOT 量表上，3 分以内算同级。
- **"完全本地"**：见上文，Composio 和 Soniox 是云服务。

## 和 operad bot 的对照（判断）

对照的是 ADR 0025、0030 到 0033 和 `docs/backlog/operad-bot.md`。

**operad 强的地方**

1. 不让模型替人决定。Linger 的审批靠模型评审，提醒规则每晚由模型改写。operad 的访问档是确定的 JSON 规则（ADR 0025），改 bot 的技能、MCP 服务、设置和定时任务只走提议（ADR 0030 D4、D11）。
2. 后台运行更严。不是人当场发起的运行，每次对外写都先问（ADR 0025 D10 到 D12）；Linger 把用户保存的 routine 当成当场授权。
3. 体量小：一个 Bun 进程加 SQLite。
4. 手机：原生 iOS app 和 Telegram，跨设备是同一个 chat。Linger 的文档里只有网页和桌面。
5. 可扩展：一句话描述需求，agent 写出 flow 或插件；Linger 是功能固定的成品。

**operad 弱的地方**

1. 知识库和记忆还没做（`brain` 的三个 flow、`digest`）。差距最大的一块，也是 `operad-bot.md` 验收里本来就有的。
2. 没有主动性，只有定时 prompt。
3. 外部应用：来源插件还没做，邮件和日历没有计划。
4. 桌面操作不做，浏览器还在 `operad-bot-mcp.md`。
5. 本地模型的选型、安装和调度没有；语音不做；没有安装包。

缺口里的 4、5 两条和 `operad-bot.md` 里"不做"的范围一致，目标是替掉自己的 OpenClaw 场景，不必追。

## 对 operad 的含义（判断，owner 未定）

1. **`brain:review` 可以照它的"逐节提议、程序核对"做**：列表按程序分配的 ID 一次改一条，摘要改写要给理由，改写要保留旧文本的来源，变更记录由程序写。这比 `operad-bot.md`「记忆和知识库：提议」里"丢掉太多就作废"更细，两者不冲突。
2. **"一页一个实体"是知识库怎么组织的一个现成答案**（`operad-bot.md` 里说组织和检索是最关键的两件事，还没定）。和不要求用户改 Obsidian 目录结构怎么并存，要另想。
3. **只用全文检索、带多种说法、两个分开的列表**，印证「记忆和知识库：提议」先做 FTS5、向量以后可选的方向。"说没记过之前先搜原始记录"可以写进 `brain` skill。
4. **记忆摘要作为消息的附注带进去，不进系统提示**，是待决问题 10（索引在会话里是否冻结）的第三种做法：不冻结，也不废掉提示缓存。
5. **主动提醒的学规则和"没有模型替用户改规则"冲突**。想要类似的效果，只能做成提议：bot 提出一条规则，人批准才生效（ADR 0030 D4 的形状）。
6. **AlterEgo 从不问用户**，是 worker 提问没人能答这个问题的一种结构上的解法：问题进报告，由上一层决定。和 ADR 0008 在步骤里问人的做法不同，值得在 worker pool 的设计里对比一次。
7. **模型调度的自适应并发和换出**，以后 worker pool（ADR 0021）要在一个本地模型或一个订阅上跑多个 worker 时可以参考；现在不需要。
8. **写操作带 operation ID、结果不明不重发**，和 ADR 0025 D11 认对外写是同一类问题的另一半，来源插件和通道做对外写的时候用得上。

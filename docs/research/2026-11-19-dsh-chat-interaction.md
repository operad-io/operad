owner 说"感觉我们的对话还是很多摩擦"，让对照 DeepSeek Harness（`dsh`）的前端。对照之后 owner 定了"1-5 都做"（2026-11-19），即本文"五处"一节的全部五项。事实和判断分开写：前两节是事实，最后一节是做法的建议，细节还不是决定。

- **dsh 一侧**：读的是 `github.com/deepseek-ai/deepseek-harness` 提交 `2e39e704`（2026-11-18）的文档和前端源码，没有安装运行。读的人是子代理，写这份笔记时没有逐条回到源码复核；标 **文档** 的出自它的 README 或 `docs/`，标 **源码** 的子代理读过实现，标 **未核** 的没有定论。
- **operad 一侧**：读自 operad `main`（`63fcf12e` 前后）和 operad-desktop 的代码、ADR 和 backlog。路径里 `op/` 是 operad，`dk/` 是 operad-desktop。

## dsh 是什么

`dsh` 是一个自带 agent 循环的运行时，MIT，TypeScript，标着 developer preview。它的 Web 聊天是本机 Host 进程的客户端：页面经一条连接调用 Host 的 RPC（`/api`），会话事件走同一条连接推回来。收件箱、等待中的审批和提问、未读状态都在 Host 上，所以任何一个标签页都能发消息或回答，先到的回答生效（源码，`packages/api/gateway/src/index.ts`）。

## 五处对照

### 1. 流式显示

| | dsh | operad |
|---|---|---|
| 进行中的文字 | 每个动画帧发布一次，Markdown 增量渲染（源码，`conversation-nodes/assistant.ts:332-336`） | 没有推送流：每次服务端变化事件后重读这一步日志的尾部（ADR 0027 D4、ADR 0019；`dk/src/mainview/chats.tsx:535-657`） |
| 换行 | 保留 | 进行中的文字和中途文字被压成一行，到最终消息才恢复（`op/packages/chat/src/views.ts:221, 775`） |
| 滚动 | 离底部 24px 内跟随；滚开就停并显示"回到底部"；发送后恢复跟随（源码，`use-chat-reading.ts`） | 未查 |
| 状态 | 一个工作指示加已用时间；工具名在过程组的标题里 | 三个点、Starting / Thinking / Running `<tool>`、从发送起算的时间（ADR 0026 D13） |

operad 的 backlog 写的是推送流"不够顺再加"（`op/docs/backlog/operad-conversation.md:20`）。

### 2. 回复过程的结构

**dsh（文档，`packages/client/ui-chat/src/client/conversation-nodes/README.md`）**

- 一行是一个"节点"，由同一 `(kind, id)` 的事件折叠而成；每个节点声明自己在 `exchange > input > turn > process` 里的位置。
- 一组过程收集一轮里相邻的过程内容，步数变化不拆组，答复和输入才拆。
- 完成的一轮是：输入、"用时 1 分 3 秒"、答复、页脚。只有结束的轮才折叠；折叠隐藏过程，永远不隐藏答复。
- 折叠行的摘要是类别词，不带计数（"读了文件并运行了命令"）；进行中的标题显示最近开始的那个工具的细节。
- 显示有四档：紧凑、标准、详细、完整，默认详细；折叠时机可选"完成时"或"下一条消息时"。
- 推理是一行折叠的"Think"，带首行预览。工具在名字已知时就出现"准备中"一行；长输出超过 16 行折叠；没有实时 stdout。
- 改动的文件在这一轮的末尾有一张卡片，带 +/- 行数，点开是 diff 审阅页（文档，`ui-deliverables/README.md`）。

**operad**

- 服务端给的是 Markdown 行：工具调用是 `tool <名字> <用时> \`输入\``，思考是 `>` 引用（`views.ts:182-225`）。
- 工具输出记录了前 4 KB 加完整文件，但聊天里从不显示（`views.ts:777-781`；ADR 0027 D2）。
- 桌面把连续的思考和工具行折成一行（"Thinking · Bash ×3, Read"），默认折叠（`chats.tsx:968-1005`）。
- 结构化的可折叠工具卡片已决定要做但还没做（ADR 0027 D3；`op/docs/backlog/operad-chat-next.md:26`）。聊天里没有 diff。

### 3. 出错和中断后的恢复

**dsh**

- 自动重试显示成一行"正在重试模型请求 (2/5) · 3 秒"，带倒计时，可展开看原因；5 次，退避 500 ms 到 10 s（源码，`MessageItem.tsx:63-128`）。
- 终止性失败是一行"这一轮失败了"加错误码；限流、服务端错误、超时、传输错误、空回答、流被关闭之后，空的输入框里出现"继续生成"（源码，`session-controller/src/continuation.ts:9-11`）。
- 停止：按钮，或 500 ms 内按两次 Esc。半截答案保留，标"已停止"，下一轮交给模型；排队的消息保留（文档，`agent-loop/README.md`；源码，`session-controller/src/commands.ts:528-541`）。停止后队列是否自己重新开始，**未核**。
- Host 崩溃后，这一轮被关成"被打断"，不续跑（文档，`docs/subsystems/persistence.md:108-112`）。
- 没有重新生成、改了再发、回退；恢复只有"继续"和分叉。

**operad**

- 失败是一行文字，带供应商的消息（ADR 0027 D7）。恢复靠 `/retry`，它只在上一次失败或被停止后可用，否则拒绝（`op/packages/chat/src/index.ts:619-664`）。
- 停止后半截文字保留，标 `*stopped*`；期间到达的消息不会自己被回答，提示用 `/retry`（`index.ts:522`）。
- pi harness 关掉了 pi 自己的重试（ADR 0023 D3）。
- serve 重启打断的回复：这一步是 `replay: "unsafe"`，走到 `cancelled`，不留条目也不留失败行（`index.ts:78`；见 `2026-11-19-pi-durable.md` 第 2 节）。此时 `/retry` 应当会拒绝，因为既没失败也没被停止，**未核**。

### 4. 回复中途发消息

**dsh（源码，`agent-loop/src/inbox.ts`、`agent.ts:348-406`、`queue/QueueDock.tsx`）**

- Host 上有两个收件箱：下一轮（排队）和下一步（插入）。设置里选 Enter 做哪一种，默认排队；Cmd/Ctrl+Enter 做另一种。
- 认领规则：一轮开始时取全部插入的消息加恰好一条排队的消息，所以每条排队的消息各成一轮；步与步之间只取插入的。
- 排队的消息在输入框上方的一栏，写着"N 条排队的消息"，每条可以改、删、改成插入。被认领之前不进聊天记录。没有找到调整顺序。
- 插入的消息显示成运行指示之后的气泡：先是本地回显，再是 Host 的"待插入"，最后被落定的消息原位替换。

**operad**

- 纯文字消息在同一次回复里交给 agent，排在正在跑的工具之后（claude 和 pi 声明了 `takesMessagesMidRun`）；带附件的消息和 radian 上的消息等下一轮（ADR 0026 D3；ADR 0037 D9 说没有 `/steer`）。
- 桌面先把消息淡色画在末尾，等服务端的副本到了按时间放进回复的条目里；服务端的顺序由 T-0565（已合并）和 T-0566 定。
- 发出去的消息不能改，也不能撤。

### 5. 提问、审批和计划审阅

**dsh**

- 审批、提问、计划审阅都占用输入框的位置，不是弹窗也不在记录里；输入框留在下面，草稿不丢。一个会话一次只显示一个，优先级是计划审阅 > 提问 > 审批（源码，`ui-session/src/client/index.ts:470-480`）。
- 提问（`ask_user_question`）是一张卡片：多个问题翻页，单选或多选，"其他"自由填写，每题可跳过，推荐项默认选中。关掉卡片后可以从工具行重新打开。回答显示成用户气泡；打一条普通消息不算回答（文档，`ui-user-questions/README.md`）。
- 计时提问是可选的：聚焦时倒计时暂停，到期后模型拿到"待定"，问题仍可回答（文档，`docs/subsystems/user-questions.md`）。
- 计划审阅：`exit_plan_mode` 出一张卡片（标题、两行摘要、"看全文"、要求修改 / 批准），全文在右侧栏只读打开。要求修改会结束这一轮，用户用普通消息写反馈（源码，`packages/plan/plan-mode/src/index.ts:321-372`）。
- 审批只有"允许一次"和"拒绝"；长期许可只能靠切换权限预设。没有找到超时。

**operad**

- 问题和权限请求都走 `ctx.ask`，成为这个聊天的待处理项（ADR 0026 D6）。桌面把它画在记录底部的一张卡片里，同时出现在 Pending 里（`chats.tsx:1220-1391`）。
- 选项比 dsh 多：允许一次、总是允许、拒绝、开工作区（ADR 0028 D3）。
- 没有专门的提问表单；claude 的 AskUserQuestion 怎么处理，没查到。
- "Plan only" 是只读的访问级别，不是计划审批流程；没有计划审批卡（`op/packages/harness/claude/src/access.ts:54-63` 把 ExitPlanMode 放在免检查的工具里）。
- 宽限期 600 秒，之后这一步以 `waiting` 结束，问题只留在待处理里，不提醒也不过期（`operad-chat-next.md:16` 记着一个问题挂了三天）。这一点 dsh 也没有解决。

## 不用学的地方

- **审批选项**：dsh 只有两个，operad 的更细。
- **通知**：dsh 一轮结束没有任何系统通知、声音或角标；operad 有桌面通知和 Telegram。
- **发送后清空输入框**：dsh 等 Host 接受才清空；operad 立刻清空、被拒再放回（T-0169），手感更快。

## 五项的做法建议

下面是我的建议，范围和拆分由主控会话和 owner 定。

1. **流式显示**
   - 服务端：给进行中的回复一条推送通道，或者至少让现有的尾部不再压掉换行（`views.ts:221, 775`）。涉及 ADR 0019、0027 D4、0029。
   - 客户端：增量渲染 Markdown；滚动规则照 dsh 的"离底部近才跟随"。
   - 先量再改：`/status` 已经有"首次输出 X 秒"（T-0486），改之前记一组数。

2. **回复过程的结构**
   - 就是 ADR 0027 D3 的结构化块。dsh 的规则可以直接当规格：折叠隐藏过程、不隐藏答复；摘要用类别词；一轮末尾写用时；工具输出超过若干行才折叠。
   - 工具输出已经记录了，缺的只是显示。
   - 改动文件的卡片和 diff 可以放到第二步。

3. **出错和中断后的恢复**
   - 给失败、停止、被打断的回复一个"继续"动作，三个客户端都能用；`/retry` 的可用条件放宽到"被打断"。涉及 ADR 0037。
   - serve 重启时也记下已完成的条目和一条被打断的记录，否则没有东西可以"继续"。这和 `2026-11-19-pi-durable.md` 建议先补的缺口是同一件事。
   - 自动重试：pi 的重试今天被关掉了（ADR 0023 D3）。要不要打开并显示成一行倒计时，需要 owner 定。

4. **回复中途发消息**
   - 最小的一步：还没被 agent 接走的消息（带附件的、radian 上的、agent 没取的）有一个可见的位置，可以撤回或修改。
   - 要不要像 dsh 一样区分"排队"和"插入"两种发送，是更大的改动；ADR 0037 D9 目前明确说没有 `/steer`。
   - 这里会出现新的用户可见的词（例如"排队"），按仓库规则要 owner 批准。

5. **提问和计划审阅**
   - 提问表单：多个问题、选项、自由填写、跳过。数据从哪来取决于各 harness 怎么上报问题（claude 的 AskUserQuestion、radian 的 `ask_user`、pi 的工具），要先查清。
   - 计划审阅卡：claude 的 ExitPlanMode 今天免检查通过；要做审阅卡就得让它变成一次询问。"计划"这个词今天属于 `dev` 插件，聊天里用它要 owner 批准。
   - 位置：dsh 把这三种等待都放在输入框的位置并排优先级。operad 今天放在记录底部；要不要挪，是桌面和 iOS 的设计决定。

## 没有验证的事项

- dsh 的全部行为没有运行验证，源码引用没有二次复核。
- dsh 停止后队列是否自动继续；审批等待时并行的其他工具调用是否继续。
- operad 在 serve 重启后 `/retry` 是否真的拒绝。
- operad 桌面今天的自动滚动规则。
- claude 的 AskUserQuestion 在 operad 里今天怎么呈现。

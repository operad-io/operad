# 长对话：同类产品怎么管会话、上下文、定时结果和记忆（2026-11-23）

owner 问的问题："现在 chat 太多了，能有长对话解决对话越来越多的情况么"，随后要求看 Claude Duet、pi-durable、OpenClaw、Telegram，再看更多竞品和记忆管理。决定已经写进 `docs/backlog/operad-long-chat.md`（计划 P-0143）；这里留调研的事实和出处。

出处的标法：**厂商** 是读了厂商文档、更新日志或源码里的文档；**摘要** 是只见到搜索结果的摘要，没打开原页；**第三方** 是评测、博客或论坛；**未核** 是没有验证。调研由六次只读的网页调查完成，没有运行任何一个产品。数字都出自所标的出处，没有出处的不写数字。最后两节是判断，不是决定。

记忆一侧在 `2026-11-15-memory.md` 已有的内容不重复，第 5 节只写那之后的变化和当时没覆盖的系统。pi-durable 见 `2026-11-19-pi-durable.md`：它解决一次回复跨崩溃续跑，和 chat 的数量、上下文的长度无关，这次没有新结论。

## 一览

- **单一长线程不够用**：Claude Duet 默认一个持续的线程，有用户说"撑了大约两周"，补救是按主题的频道加任务列表（第三方）。
- **自动翻篇在退场**：OpenClaw 的按天、按空闲重置默认关，Hermes Agent 把它从核心里移除了；两家都靠压缩和显式的 `/new`（厂商）。
- **定时运行不是对话**：OpenClaw、Hermes 的定时运行都在用完即弃的会话里跑，结果靠送达回到聊天，无事可报不送达，失败必送达（厂商）。Manus 的旧设计每次新建任务，用户要跨任务找结果，2.0 改了（厂商）。
- **先修剪，后压缩**：屏蔽旧的工具输出成本约为一半，解决率与模型摘要持平或略高（论文）。修剪每次都让提示缓存失效，所以要等缓存过期；压缩相反，要趁缓存还热（厂商）。
- **压缩丢得最多的是"动过哪些文件"**：Factory 评测的各家方案在这一项都最低（厂商自测）。pi 和 OpenCode 的摘要带文件清单（厂商）。
- **用交接代替压缩**：Amp 去掉了压缩，改成按目标生成简报的 `/handoff`（厂商）。
- **用户怎么在很长的线程里找东西，几乎没有 agent 产品写**；消息类应用有按日期搜索、置顶、未读摘要（厂商帮助页，多数只见摘要）。
- **Telegram 的 bot 私聊支持话题**：Bot API 9.3 起（厂商）。

## 1. 对话怎么组织

**Claude Duet**（Anthropic，2026-10-21 研究预览）

- "one ongoing thread"，打字或语音，独立于 Claude 应用（厂商）。
- 频道由用户按主题建，和主线程并存；任务各自在独立线程里跑，任务列表让人看清 agent 在做什么（第三方，一位评测者）。"Groups" 没有可读的出处。
- 每天一次晨报，每隔几小时检查一次，"only when something needs your attention" 才发消息；任务完成或要审阅时通知（厂商）。
- 用户的说法（第三方）："I treated it like one long text conversation. That worked for about two weeks."之后各种内容混在一个 chat 里。另一位说 agent 太安静，她忘了开着的线程，分好类只解决一部分问题。
- 压缩、记忆怎么写、搜索、归档：公开资料都没写。讲频道细节的那篇在付费墙后，只读到开头。

**OpenClaw**（厂商，`docs/concepts/session.md` 等）

- `session.dmScope` 默认 `main`：所有私聊渠道共用一个会话。其他值 `per-peer`、`per-channel-peer`（文档标为推荐）、`per-account-channel-peer`。
- `session.groupScope` 默认 `per-group`；带话题的会话键有 `:thread:<id>` 后缀。
- 重置默认 `mode: "none"`。可选 `daily`（`atHour` 默认 4，网关所在机器的本地时间）和 `idle`（`idleMinutes`，默认值文档没写）；两个都设时先到的生效；`resetByType`（`direct`、`group`、`thread`）和 `resetByChannel` 可分别设。心跳、定时、系统事件不延长空闲计时。
- `/new`、`/reset`：旧会话不改写，记录保留。`/new <model>` 同时换模型。
- 清理 `session.maintenance`：`pruneAfter: "30d"`、`archiveDashboardAfter: "7d"`、`maxEntries: 5000`（归档的不计）。超限时先归档最旧的普通会话，记录不删、可搜可恢复；定时、心跳、子 agent 这类会话可以直接删。
- 没读到的页：main-session、session-search、memory 的落盘配置、subagents 的归档默认值。

**Hermes Agent**（厂商）

- Telegram、Discord 私聊每个 chat 一个会话；只有 `/new`、`/reset` 或压缩产生新会话。
- 空闲和每日重置已从核心移除，旧的 `session_reset` 配置被忽略，只能靠社区插件恢复。文档没说原因。
- 压缩生成"续接会话"，标题沿谱系编号（"my project #2"）；首轮之后后台自动起 3 到 7 个词的标题，`/title` 可改。
- 会话清理默认关，开了之后 `retention_days` 默认 90；置顶的会话不被自动归档。

**其他**

- **Letta**（厂商）：一个 agent 多个对话，共享长期记忆；`/new`、`/resume`、`/fork`，`/btw` 在后台分叉回答旁问。
- **ChatGPT**（厂商）：定时任务绑定在某个对话上；活跃任务上限按套餐 3 到 15 个；删除对话会暂停它的任务。消息菜单有"Branch in new chat"。
- **Claude 应用**（厂商）：每个项目有自己的记忆；搜索历史对话显示为工具调用，引用带回到原对话的链接；有不写记忆的隐身对话。
- **Manus**（厂商）：Scheduled Tasks 2.0 每次运行可选"在同一任务继续"或"另起任务"。Telegram 的专用聊天和网页端是同一对话（第三方）。
- **Lindy**（厂商）：routine 送到"默认主动渠道"，可逐个开关而不删除。对话结构和压缩文档没写。
- **Pi（Inflection）**（厂商）：很长的对话"可能摘要"早期消息。
- **Poke**：官方文档只确认可用的渠道；内部机制只有一份基于泄露提示词的重写（第三方）。
- **Zo Computer**（摘要）、**Dot**（已停运，第三方摘要，未核）：没有可用的信息。

## 2. 上下文怎么保持有界

**压缩的触发和保留**（厂商，除另标）

| 产品 | 触发 | 保留和摘要 |
|---|---|---|
| OpenClaw | 窗口的 80% 与（窗口减保留量）中较小的 | 最近 `keepRecentTokens` 20,000 原样；摘要上限 `maxSummaryChars` 16,000；完整历史留在磁盘；压缩前可跑一轮静默的记忆落盘 |
| pi | `contextTokens > contextWindow - reserveTokens`（16,384） | 最近 20,000 token；从不在工具结果处切断；固定小节 Goal、Constraints & Preferences、Progress、Key Decisions、Next Steps、Critical Context，加 `<read-files>` 和 `<modified-files>`；更新上一份摘要而不是重写 |
| Claude Code | 默认在模型的上下文上限；`/autocompact` 可设，最小 100K | 保留"your requests and key code snippets"；摘要提示词的结构文档没写 |
| Codex | `model_auto_compact_token_limit`；回合结束时另有 `model_post_turn_compact_threshold_percent` | `compact_prompt` 可覆盖；`/responses/compact` 返回加密、不可读的压缩项 |
| OpenCode v2 | 缓冲 15%（至少 16k） | 保留约 15,000 token；小节含目标、决定、进展、阻碍、下一步、相关文件 |
| Goose | min(窗口的 80%, 225,000 token) | 压缩后历史仍然可见 |
| Gemini CLI | `model.compressionThreshold` 0.5 | 历史窗口 150,000，保留 40,000 |
| Anthropic API | `compact_20260112` 默认 150,000，最低 50,000 | 按需压缩（beta）可保留最近几轮原文、可后台运行；摘要带不走图片、文档和抓取的 URL |

**压缩之前更便宜的步骤**

- OpenClaw 的修剪（厂商）：只动 `toolResult`；`contextPruning.mode: "cache-ttl"`，等缓存 TTL 过了才做（默认 `5m`，Anthropic 登录是 `1h`）；用量约 30% 以上时把超过 4,000 字符的结果留头尾各 1,500；约 50% 以上且可修剪的超过 50,000 字符时整条清掉、留占位符；最近三个助手回合不动。
- Anthropic `clear_tool_uses_20250919`（厂商）：默认 100,000 输入 token 触发，保留最近 3 次；每次清理都使缓存前缀失效并重付写入费；`clear_at_least` 让每次清理值回成本。
- Gemini CLI（厂商）：工具输出屏蔽（保护 50,000 token 和最近一轮，最小可修剪量 30,000）；超过 40,000 字符截断。
- Cursor（厂商）：长的工具输出写到文件，agent 自己 `tail` 或搜索。
- Claude Code 的"microcompact"不在现行文档里（未核）。

**缓存**（厂商）

- Anthropic：TTL 5 分钟或 1 小时，命中即续期；写入 1.25 倍或 2 倍，读取 0.1 倍（较新的模型更低）。
- Claude Code：压缩请求在缓存热时读缓存，冷了整段历史按未缓存计费；1 小时 TTL 下可在空闲时压缩（`idleCompaction`，文档只有一行说明）。
- 空闲后缓存未命中实际多花多少，没有找到公开的实测。

**压缩的替代**（厂商）

- **Amp**：去掉了压缩。`/handoff <goal>` 在新线程里起草提示词加文件清单，发送前可改；`@T-…` 引用别的线程，`read_thread` 由另一个模型只抽相关部分，`find_thread` 搜线程。它的理由是压缩是"summary on top of summary"。
- **Cline**：`new_task` 带 `<context>` 块，先向用户提议。
- **Claude Code**：`/rewind` 可以只摘要某条消息之前或之后的部分；`/branch`；分叉读父会话的缓存。
- **Codex**：`/fork`、`/side`（临时的旁聊）。**Zed**："New From Summary"。**pi**：`/tree` 把放弃的分支摘要进新分支。

**压缩后重新带上什么**（厂商）

- Claude Code：根目录的 `CLAUDE.md`、自动记忆、技能描述、计划、新的 git 状态；最近改过的最多五个文件（超过 5,000 token 的只给路径）；调用过的技能正文（每个 5,000、合计 25,000）；后台任务的提醒。
- Cursor：一个指向聊天记录文件的引用，让 agent 能搜摘要丢掉的内容。

**用户看到什么**（厂商）

- Claude Code：`/context` 分项；"Summarized conversation" 标记；离开 3 分钟以上后一行回顾（最多 400 字符，`/recap`）；压缩后立刻又满时报错而不是循环。
- Goose：带颜色的用量条。Roo Code：可展开的摘要行，带 token 和费用。Zed：横幅建议开新线程。

**实测**

- arXiv 2508.21433（论文）：SWE-bench Verified 上，屏蔽旧的观察结果成本约为原始 agent 的一半，解决率与模型摘要持平或略高。
- Factory（厂商自测）：36,611 条生产消息上的探针评测（回忆、产物、延续、决定），模型评分；Factory 3.70、Anthropic 3.44、OpenAI 3.35；产物（文件）跟踪各家都最弱，2.19 到 2.45（满分 5）；只看压缩比是差的指标。
- Anthropic（厂商，基线和规模未公布）：记忆工具加上下文编辑比基线高 39%，只用上下文编辑高 29%；100 轮网页搜索评测 token 降 84%。
- Chroma（厂商研究）：18 个模型随输入变长而变差。
- arXiv 2504.13171（论文）：sleep-time compute 的收益，任务是推理题，不是对话。

## 3. 定时和主动的结果怎么出现

**OpenClaw**（厂商；定时现在叫 Automations）

- 运行目标四种：`main`（走主会话的队列）、`isolated`（每次一个新会话，键 `cron:<jobId>`）、`current`（发起它的对话的子运行，读那个对话的一段尾部）、`session:<key>`（固定名字的持久会话，跨次保留上下文）。
- 送达三种：`announce`（把结果发到目标，输出写进那个聊天的记录）、`webhook`、`none`。
- 无事可报回 `NO_REPLY`，不送达、不算失败，记下 `deliverySuppressionReason`。
- `cron.sessionRetention` 默认 `24h`，清掉独立运行的会话；运行历史保留 7 天，每个任务最多 2,000 行。
- 心跳已并入 Automations：一个"Proactive check"任务，默认不启用，启用后默认每 30 分钟，用 agent 的主对话。

**Hermes Agent**（厂商）

- 定时任务在全新的会话里跑。送达的消息默认不进聊天历史，`cron.mirror_delivery`、`attach_to_session` 可改。
- 输出含 `[SILENT]` 就不送达，但输出仍然存盘；失败的运行一定送达。
- 送达的消息默认带页眉页脚，标明任务名。

**消息类应用里的长线程**（厂商帮助页；多数只见摘要，未逐页核对）

| 做法 | 产品 |
|---|---|
| 按日期搜索 | WhatsApp（搜索里选日历日）、Discord（before/after 过滤） |
| 置顶 | WhatsApp（最多 4 条，带时长）、Discord（每频道 250 条）、Telegram |
| 收藏 | Telegram Saved Messages（可加标签）、Slack Saved |
| 单聊内的话题 | Telegram bot 私聊：Bot API 9.3 起支持，9.4 起 bot 可建话题，10.4 有话题链接，10.5 有侧栏 |
| 未读摘要 | Slack（未读 10 条以上有 Summarize，另有每日 Recap）、WhatsApp（默认关）、iMessage（Catch up）、Discord（部分服务器） |
| 从某条消息分支 | ChatGPT |
| 模型搜索旧聊天 | Claude（引用带回链）、Gemini（来源里标"Previous chats"） |
| 折叠自动消息 | 没找到 |

## 4. Telegram 在 operad 里今天怎么管

出自 ADR 0033 D5 和 ADR 0028 D6。一个私聊对应一个 chat，第一次发消息时自动开并绑定；chat 关闭后下一条消息开新的；只有私聊，没有绑定已有 chat 或换 bot 的动作；app 里开的 chat 不绑任何通道。所以 Telegram 一侧今天已经是长对话，缺的是 `/new`、pi 的压缩，以及和 app 是同一条线。

## 5. 记忆：2026-11-15 之后的变化和当时没覆盖的

**已覆盖系统的变化**

- **Codex CLI 0.165.0**（厂商，2026-10-27）：新 profile 默认用 memory v2，可导入外部 agent 的记忆。配置参考仍写 memories 默认关（摘要，未核）。
- **OpenClaw**：压缩前保存成为插件钩子，失败不挡压缩（厂商，2026.10.1）。新的 Knowledge 插件：claim 带证据摘录，显式取代旧 claim（厂商）。11 月的分页压缩等条目只见更新日志的聚合（第三方）。
- **Claude Code**（厂商）：界面显示"Saved 2 memories""Recalled 2 memories"。
- **ChatGPT**（厂商）：回复下方可出现 Sources，指向用到的过去对话、保存的记忆、文件；记忆摘要可纠正或选"Don't mention this again"。dreaming 会随时间改写："要去新加坡"变成"2026 年 7 月去过"。
- **Gemini**（第三方，Engadget）：记忆摘要是分类列表，可改可删，保留改动历史。

**当时没覆盖或覆盖浅的**（厂商）

- **Zep / Graphiti**：事实带四个时间戳（`valid_at`、`invalid_at`、`created_at`、`expired_at`）；矛盾时旧的失效而不是删除；进上下文的格式是 `FACT (Date range: from - present)`；检索不调模型。
- **Honcho**：消息同步落库，后台逐条抽结论；dream 先演绎后归纳，过期的结论删除并新建，留 `replaced_by`；会话摘要每 20 条和每 60 条各一档。
- **Supermemory**：文档和抽取的记忆分开；关系有 updates、extends、derives；`isLatest` 保留历史；临时事实到期掉出；画像分稳定和当前两部分。
- **Letta**：记忆块有 label、description、value、limit；后台整理在若干步后或压缩时触发，可选"agent 先复核再应用"。
- **Mastra observational memory**：默认 3 万 token 触发观察，留约 6,000 token 最近消息；`retrieval: true` 时每组观察链回原消息，`recall` 工具读原文。
- **Anthropic 托管 agent 的 Dreams**（研究预览）：输入一个记忆库加 1 到 100 个会话，输出新的记忆库，输入从不被修改，可审阅后丢弃。
- **NanoClaw**：记忆只在新上下文创建时注入（启动、清空、压缩后），恢复会话时不注入；每个加载的文件上限 16,000 字符。
- **Lindy**：记忆文件每次保存一个版本，可恢复。
- **OpenClaw Active Memory**：默认 `escalate`，只有消息问到过去且没有强匹配时才跑阻塞的子 agent；文档没给延迟数字。
- Cognee、MemOS、A-MEM：只见摘要，没有可报的机制（未核）。

**安全**

- arXiv 2608.21230（单作者）：污染 1.2% 的语料，准确率从 0.850 降到 0.300；四级写入扫描拒掉 360 条毒记忆中的 0 条；按来源降权等于没有防御，只有排除不可信内容才有效，代价是合法的不可信证据也丢了。
- arXiv 2609.13889：跨会话攻击的成功率 OpenClaw 55.5%、Claude Code 81.7%。
- Microsoft（厂商）：60 天内见到 31 家公司的 50 多条"记住某公司可信"的预填提示链接。

**生产里怎么评测**（厂商）

- Letta Context-Bench V2（私有，无分数）：从生产轨迹挖失败模式，量遵守、检索、概括、整洁。弱模型把纠正追加成新条目、留下矛盾；一条轨迹里模型把常设指令当成注入删了。
- Mastra：把生产里答错的对话加进回归集，用户的纠正算一次检索漏失。

## 判断：哪些进了决定

以下是看法。已经进 `operad-long-chat.md` 和 P-0143 的是 owner 2026-11-23 定的，这里只说它们的来由。

- **定时运行不是 chat、结果送达主 chat、无事可报不送达**：OpenClaw、Hermes、Duet 三家一致，Manus 的旧设计是反例。
- **自动翻篇这一轮不做**：OpenClaw 默认关，Hermes 已移除。
- **先修剪后压缩，修剪等缓存过期**：论文和 OpenClaw、Anthropic 的文档一致。
- **多话题不做，bot 当频道用**：Duet 的教训说明单线会乱，但多话题要绑定动作和新词；Telegram 的话题接口已核实可用，以后重提时走这条路。

## 判断：还没排的

按估计的价值排，都还不是决定。

1. **回来时的回顾**：离开期间的 routine 结果和进展合成一条。出处：Slack、WhatsApp、iMessage、Claude Code。
2. **长 chat 里分段和跳转**：`/new` 和压缩产生的每一段有标题，可按段、按日期跳转和搜索。出处：Hermes、WhatsApp、Discord。
3. **回复里显示写了、用了哪些记忆**：出处 Claude Code、ChatGPT。提示文字是新的用户可见词，要 owner 批准。
4. **用自己的 chat 记录做记忆回归集**：出处 Letta、Mastra。
5. **梦境整理时改写带时间的句子，短期事实带到期日**：出处 ChatGPT、Zep、Supermemory。`2026-11-15-memory.md` 的第 6 条已提"记日期、取代不删"，这里是具体格式。
6. **主 chat 里的"不记这段"**：出处 Claude、ChatGPT。

只记着的：旁问和分叉（`/btw` 已在命令第二批）；从某条消息分支和只压缩中间一段；定时结果放进 Telegram 话题；routine 选续接上下文或每次全新；梦境整理按压缩或步数触发加复核；只在问到过去时主动回想（没有实测，NeurIPS 2026 的一篇论文摘要提示过量检索有害）；稳定画像和当前状态分开存。

不必做的：记忆的写入扫描（上面的论文里拦下 0 条）。

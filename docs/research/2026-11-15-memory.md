# 同类产品的记忆系统，以及对 operad bot 记忆的含义（2026-11-15）

为 `operad-bot.md` 的 bot 记忆设计（"这个插件和记忆的管理以后单独设计"）和 ADR 0026 D7（记忆是 Markdown 知识库，由 skill 读写）做的调研。事实和判断分开写：前七节是事实，标 **厂商** 的读过厂商的文档或源码，标 **第三方** 的只有第三方出处，标 **未核** 的只见过搜索摘要或没找到可靠出处；最后一节是判断，都还不是决定。基准分数大多是厂商自报、评分方式各不相同，只能看方向。

## 一览

| | 存什么 | 谁写、何时 | 怎么进上下文 | 人的控制 |
|---|---|---|---|---|
| OpenClaw | `MEMORY.md`、`USER.md`、每日笔记，SQLite 索引 | 当场写文件；压缩前静默落盘到每日笔记；夜间整理写 `MEMORY.md` | 固定文件每次注入（单文件 2 万字符）；其余靠 FTS5 加向量搜索 | 直接改文件；无写入前批准，事后看 `DREAMS.md` |
| Hermes Agent | `MEMORY.md` 2,200 字符、`USER.md` 1,375 字符；会话库 FTS5；技能 | `memory` 工具；每 10 轮由后台分身回看一次 | 会话开始时冻结注入，当场写的下个会话才看到 | 批准开关默认关；满了由 agent 手工腾位置 |
| NanoClaw | `memory/` 目录，一个概念一个文件 | 当场写文件 | 只注入索引和一份记忆守则（各 1.6 万字符），其余 `rg` | 直接改文件 |
| Claude Code | `MEMORY.md` 索引加主题文件 | 当场写文件 | 索引前 200 行或 25KB，主题文件按需读 | 直接改文件 |
| Codex CLI | 原始摘要、合并后的 `MEMORY.md`，目录自带 git | 离线两阶段抽取和合并；干活的 agent 不改记忆 | 注入摘要，回复里标出用了哪几行 | 默认关闭；30 天没用到的掉出去 |
| Copilot | 带代码引用的仓库事实 | agent 干活时写 | 会话开始注入最近的 | 用前对着当前分支核对引用，90 天过期 |
| ChatGPT | 后台合成的记忆状态 | 后台整理，不问人 | 每次注入 | 只能看到一份不完整的摘要 |

## OpenClaw 和 NanoClaw

都是 **厂商**（`openclaw/openclaw` main 分支的文档和源码），用户报告另标。

- **文件**：工作区默认 `~/.openclaw/workspace`，全是 Markdown。
  - `AGENTS.md`（操作说明，人写）、`SOUL.md`（人格）、`IDENTITY.md`、`BOOTSTRAP.md`、`BOOT.md`。
  - `USER.md`：对用户的认识，写成祈使句，原地替换。
  - `MEMORY.md`：整理过的长期事实和决定。条目行尾可带注释：`<!-- trigger: ... -->`、`<!-- importance: 1-10 -->`、`<!-- project: ... -->`。
  - `memory/YYYY-MM-DD.md`：每日笔记，只追加，无限增长。
  - `DREAMS.md`：夜间整理的日记，只给人看，从不注入。
  - 每个 agent 一个 SQLite：会话、只追加的对话事件、记忆索引、嵌入缓存、整理的短期状态。
- **当场写**：agent 用普通的文件工具，memory-core 里没有专门的记忆写入工具。
- **压缩前落盘**：默认开（`agents.defaults.compaction.memoryFlush.enabled`）。
  - 一轮静默的回合，跑在对话的私有副本上，用会话的模型。
  - 触发点是窗口的 75% 和"窗口减 2 万 token 预留"里较小的那个。
  - 提示词要求只往 `memory/YYYY-MM-DD.md` 追加，`MEMORY.md`、`SOUL.md`、`AGENTS.md` 等一律只读，没东西可记就回 `NO_REPLY`。
  - 工具只给 `read` 和对当天文件的只追加 `write`。落盘失败不挡压缩。
- **会话结束**：自带的 `session-memory` 钩子在 `/new`、`/reset` 或按天、按空闲翻篇时存下最近的对话文本。
- **夜间整理（dreaming）**：默认开，每天 3 点，它是唯一应该写 `MEMORY.md` 的。
  - 晋升门槛：得分 0.75 以上、被检索命中至少 3 次、来自至少 3 个不同查询。
  - 之后由一轮不带工具的模型回合合并和取代。重写丢掉 25% 以上旧条目或超预算就作废，退回只追加。
  - 写入有哈希校验加原子改名，留前像，摘要进 `DREAMS.md`。
  - 定时任务、心跳、子 agent 的会话不产生候选。
  - `MEMORY.md` 的写入预算是 1 万字符，满了候选就推迟。
- **进上下文**：
  - 每个会话注入 `AGENTS.md`、`SOUL.md`、`IDENTITY.md`、`USER.md`、`MEMORY.md`。单文件上限 2 万字符，合计 6 万，`USER.md` 4,000；截断时加一句说明，磁盘上的文件不动。
  - 今天和昨天的每日笔记只在 `/new` 或 `/reset` 时加载；每日笔记和会话记录从不自动注入。
  - 每轮最多注入 3 条 trigger 匹配（0.65 以上）的 `MEMORY.md`、`USER.md` 条目，不调模型。
  - 工具：`memory_search`（默认 6 条，最低分 0.35）、`memory_get`（1.2 万字符）。
  - 索引：SQLite FTS5 加向量，400 token 一块、重叠 80；混合合并后对带日期的笔记按 30 天半衰期降权，再按 importance，再 MMR。`provider: "none"` 是只用 FTS。混合权重 0.7/0.3 **未核**。
  - 会话记录默认不进索引，要开实验开关。
- **范围**：按 agent。`MEMORY.md` 在群聊、频道、子 agent、定时任务的会话里由代码扣下不给。
- **控制**：直接改文件，或在控制台的文件页改；CLI 有 `openclaw memory status|search|index|reset|forget`。没有写入前的批准。新工作区会 `git init`，但不自动提交。
- **插件位**：`plugins.slots.memory` 独占，默认 `memory-core`；另有 `memory-lancedb`、Honcho、`memory-wiki`。QMD 已移除。
- **来源标记**：
  - 每条记忆在 SQLite 里记来源（`owner`、`agent`、`untrusted`、`system`），不写在正文里。
  - 一个回合里出现过联网工具的结果，这个回合之后写的都算不可信。
  - 不可信的内容能被搜到（结果包一层"不可信"），但不晋升、不自动注入。
  - 回想出来的内容不会被再抽取成新记忆。
  - 根目录的 `MEMORY.md`、`USER.md` 如果最后一次有记录的写入是不可信的，或者外部改过导致哈希对不上，就被排除出注入。
  - 文档自己承认的缺口：不声明联网来源的工具（比如读本地文件）不会染色。
- **用户报的问题（第三方，厂商 issue 区；除 #153426、#158912、#150635、#163900 读了正文，其余只看了标题）**：
  - 一次联网回合或人在外面改了文件之后，`MEMORY.md`、`USER.md` 被静默、永久地排除出注入（#153426、#158912，未修）。
  - 夜间整理不晋升："排了 N 条，晋升 0 条"（#121232）；`MEMORY.md` 到 1 万字符后停滞（#163900）；短期状态的上限把被命中的条目每晚挤掉（#150635）。
  - 原始日志片段没提炼就被晋升（#67363）。
  - 嵌入服务卡住时 `memory_search` 挂 15 秒（#128140、#136405）。
  - `session-memory` 钩子把原始模板 token 存了进去（#69943）；LanceDB 自动捕获造成持久注入（#12524）。
- **NanoClaw（厂商）**：每个 agent group 一个宿主目录，读写挂进它自己的容器。记忆是 `memory/` 目录：一个概念一个 Markdown 文件，frontmatter 只有 `type` 必填，每个目录一个 `index.md`。只有 `memory/index.md` 和 `memory/system/definition.md`（agent 可改的记忆守则）在会话开始、清空、压缩时注入，各 1.6 万字符上限。其余靠 `rg`、`find` 和链接。没有索引、嵌入、落盘回合和夜间整理。

## Hermes Agent 和其他自托管 bot

都是 **厂商**（`NousResearch/hermes-agent` main 分支的文档和源码），用户报告另标。

- **存什么**：`~/.hermes/memories/MEMORY.md`（agent 的笔记，2,200 字符）和 `USER.md`（用户画像，1,375 字符），条目用 `§` 分隔；`~/.hermes/state.db` 是 SQLite，带 FTS5 表，压缩掉的轮次仍可搜；`~/.hermes/skills/` 被称为"程序性记忆"。
- **当场写**：`memory` 工具，`target` 是 `memory` 或 `user`，动作是 `add`、`patch`、`remove` 或一批 `operations`。`replace` 已经去掉，因为模型拿它把含多条事实的条目整个冲掉。
- **后台回看**：一轮结束后，一个分身回放对话，问要不要存。每 10 个用户轮（`memory.nudge_interval`）或若干次工具迭代触发，最多 16 次迭代，只能用记忆、技能和只读文件工具。
- **压缩前落盘**：内置记忆没有；只有外部后端拿到 `on_pre_compress`。
- **批准**：`memory.write_approval` 和 `skills.write_approval` 都默认 `false`。打开后 CLI 当场问，其他通道进暂存区，用 `/memory pending|approve|reject` 处理。
- **进上下文**：两个文件在会话开始时渲染进系统提示词并冻结，带用量头（`[67% — 1,474/2,200 chars]`）。冻结是为了保住提示缓存；会话中写的落盘但看不到，下个会话或压缩重建提示词时才生效。
- **满了**：工具报错并返回现有条目，agent 必须在一批操作里先腾位置再加。没有自动整理。
- **`session_search`**：纯 FTS5，"no LLM summarization, no truncation"；三种用法：关键词发现、围绕一条消息滚动、浏览最近的。
- **外部后端**：一次一个，和内置文件并存。接口 `MemoryProvider` 有 `prefetch`、`sync_turn`、`on_session_end`、`on_pre_compress`、`on_memory_write` 等。Honcho 多一层对用户的"辩证"建模：每 2 轮用模型问一次关于用户的问题，上限 600 字符。
- **范围**：按 profile，不按用户或 chat。文档明说一个 profile 内不区分用户，白名单里任何人都能让 agent 搜所有人的会话。
- **遗忘**：完全重复的 `add` 被拒，其余靠 agent 手工合并；没有过期和版本。技能有 curator：14 天标为陈旧，30 天归档。
- **安全**：`memory` 工具的写入和加载时的条目过一遍正则扫描（注入、外泄、不可见字符）。文档承认扫描只管 `memory` 工具，`write_file` 和终端能直接改文件，并把这类启发式称为"not boundaries"。
- **用户报的问题（厂商 issue 区，读了正文）**：
  - 一次技能回看从 `MEMORY.md` 删掉了四条长期许可规则没人发现（#105921，已修）；模型幻觉"记忆满了"后重写了 `USER.md`（#76035）。
  - 上限太小，流程类内容占满 2,200 字符（#5320、#106786）。
  - 一个卡住的回看分身用了 1,405,754 输入 token 没有结果（#90446）；后来加了输入上限和换便宜模型的配置。
  - 技能膨胀：152 个技能里 22 个没用过的近似重复（#67582）；一次性的权宜之计变成永久规则（#136931）；没有评测证明技能有用（#96704）。
  - 文档自己写：模型会声称存了却没调工具；持续一周的网关会话让回看失效。
- **Rakazo（厂商）**：Markdown 文档存在 Postgres 里，范围是 `bot` 或 `user`，带修订。bot 的索引 `MEMORY.md` 上限 4 KB，提示词里的记忆块上限 32 KB，明确标成"是数据，不是指令"。工具是 `save_memory`、`recall_memory`、`forget_memory`、`reflect_memory`。界面能改、下载、删除。
- **OpenBot**：名字有歧义，找到两个。CopilotKit/OpenBot（厂商）：bot 形成的记忆先是 `unreviewed`，人接受之前不参与回想；每条能暂停、改、忘；只有形成它的 bot 能回想。nightly-labs/openbot（厂商，读得浅）：按 agent 和按通道的记忆存在本地库，上下文预算 8,192 字节。
- **IronClaw（厂商）**：按路径寻址的文档工作区（`daily/…`、`projects/…`），工具是 `memory_search`（FTS 加向量）、`memory_write`、`memory_read`、`memory_tree`；身份文件每次调用都注入；文档有版本。

## 托管产品

- **ChatGPT（厂商）**：
  - 旧的 saved memories 是一本短事实的记事本，模型在对话里遇到强信号就写，不问人。OpenAI 自己说它们"became stale"、"could contradict one another"。
  - 2026 年 6 月起换成后台合成（"dreaming"）：从很多对话、文件、连接的应用里整理出一个记忆状态，并随时间改写。用户只看到一份"memory summary"，官方说它不包含全部记住的东西。
  - 默认全局；项目可以设成只用项目内的记忆，双向隔离。Temporary Chat 不读不写。删对话不删派生的记忆。
  - 2025 年 12 月的逆向（第三方）：注入的顺序是会话元数据、33 条事实（每条消息都发）、约 15 个最近对话的带日期摘要、当前对话；没有检索。
- **OpenAI dots（厂商）**：每个 dot 有自己的上下文，和 ChatGPT 的记忆双向共享。"You currently cannot view, delete, or directly modify individual dot memories"，只能删掉整个 dot。Custom Rules 和记忆分开，用户可见，dot 要改它需要批准。
- **Claude（厂商）**：记忆是"a set of individual topics"，边聊边存，没有批准步骤。搜过去的对话是另一回事，走检索，以工具调用的形式可见。每个项目有自己的记忆。每个主题能看、改、删；隐身对话不存不搜。
- **Claude API 的 memory tool（厂商）**：`/memories` 下的文件，模型用 `view`、`create`、`str_replace`、`insert`、`delete`、`rename` 操作，存储在调用方手里。不注入内容，只加一句系统指令："ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE… ASSUME INTERRUPTION"。官方建议校验路径、限制文件大小、让没用到的文件过期。和上下文编辑配合：清掉旧的工具结果之前先提醒模型存一下。
- **Claude Code（厂商）**：两处。`CLAUDE.md` 由人写，启动时全量加载。自动记忆在 `~/.claude/projects/<project>/memory/`：`MEMORY.md` 索引（一行一条）加每条一个主题文件，frontmatter 的 `type` 是 `user`、`feedback`、`project`、`reference`。只加载索引的前 200 行或 25KB，超了会让模型精简索引。按仓库，所有 worktree 共用，不进子 agent。"auto dream"后台整理 **未核**。
- **Gemini（厂商）**：从保留的活动里自动得出，全局。官方承认"might not always get it right"。注入方式没公布。
- **Grok Bot（厂商）**：偏好、规则、事实和带日期的工作日志。"A Bot decides on its own when something is worth keeping. It doesn't ask first." 个人 bot 没有记忆页面。Team Bot 从队友那里学到的要 owner 或 manager 批准。厂商自己说记忆"isn't a reliable source of truth"，安全边界应该是批准和审核规则。
- **Meta Muse**：关于用户和用户提到的人的档案每小时刷新，每晚分析当天的对话；"forget"不删原始消息（第三方，TIME）。
- **Microsoft Copilot（厂商）**：存在用户 Exchange 邮箱的隐藏文件夹里；管理员有开关和 eDiscovery，没有保留策略和审计日志。
- **Windsurf（厂商）**：按工作区自动生成，不提交，"when it believes that they are relevant"时取用。
- **Devin Knowledge（厂商）**：每条带触发描述，按触发取用；Devin 的建议要人审过才存。正在并入 Skills。
- **Cursor**：编辑器里的 Memories 在 2.1 移除（**未核**）。云端 Automations 有一个 Memories 工具（厂商）：agent 写的具名笔记，按 automation 隔离，用户可改，文档提醒不可信输入的风险。

## 编码 agent 和编排工具

- **没有跨任务记忆的（厂商，读了 README 或文档）**：Vibe Kanban（README 说项目在收尾）、Claude Squad、Happy、Paseo、Orca、Kimaki、OpenAI Symphony、Amp、opencode、pi、Factory Droid。它们只靠仓库里的 `AGENTS.md`、`CLAUDE.md`。Conductor 和 OpenHands 也没找到，但只看了搜索摘要（**未核**）。claude-flow / ruflo 的 README 列了一串名词，没有描述写入、检索、衰减的机制，自己把学习循环称为"conceptual"。
- **Codex CLI memories（厂商，`codex-rs/memories/README.md`）**：
  - 目录 `~/.codex/memories/` 自己是一个 git 仓库。
  - 离线两阶段，在之后某个会话启动时跑。第一阶段：模型从符合条件的会话里各抽一份原始记忆和摘要（默认闲置 6 小时、不超过 10 天、每次启动 2 个，数据库租约，密钥脱敏）。第二阶段：在一把全局锁下，一个断网的沙箱子 agent 根据工作区差异重写合并后的文件。
  - 干活的 agent 不改记忆；"记住这个"变成一条笔记，由合并阶段应用。
  - 注入 `memory_summary.md`，回复里标出用了哪些记忆行。按使用排序，30 天没用到的掉出去。提示词写着"Memory is not proof of current behavior"。
  - 默认关闭；子 agent 和临时会话不触发这条管线。
- **GitHub Copilot Memory（厂商）**：服务端的仓库事实（主题、事实、指向代码的引用、理由）。agent 干活时用工具写。用之前对着当前分支核对引用：对的重新存并续期，矛盾的改正或降权直到删除。90 天过期。事实可能来自没合并的 PR。
- **Beads / Gas Town（厂商）**：Beads 把 issue 存在 `.beads/` 下的 Dolt 库里，`bd remember` 存项目记忆，`bd prime` 在会话开始时打印工作流和记忆。哈希 ID 避免并行冲突，原子 `--claim`。旧的已关闭 issue 被摘要压缩。Gas Town 加了持久的 agent 身份和查询前任会话的"seance"。
- **Claude Code 的子 agent（厂商）**：`memory:` frontmatter 给每种 agent 一个自己的目录，范围是 `user`、`project`（可提交）或 `local`。并行写入没有冲突处理。agent teams 之间不带任何东西到下一次。
- **Jules（厂商）**：按仓库记下任务中的偏好和纠正。
- **Cline Memory Bank（厂商）**：是一份提示词约定，不是功能：`memory-bank/` 里六个 Markdown 文件，"read all files at the start of every task"，没有大小控制。
- **并行写入**：几乎没人处理。例外是 Codex（租约加单一合并锁）、Beads、Copilot（服务端存储）。
- **效果的证据**：
  - Copilot 自己的 A/B 测试（厂商）：有记忆时 PR 合并率 90%，没有时 83%；代码审查的正面反馈 77% 对 75%。这是找到的唯一实测。
  - ETH 的研究（arXiv 2602.11988）：仓库上下文文件总体上没有提高任务成功率，不管是模型生成的还是开发者写的，推理成本涨了 20% 以上；agent 确实照着指令做了。

## 记忆框架和证据

- **框架的三种写法**：
  - 抽取管线：mem0（模型抽候选事实，和最相似的 10 条比，选 ADD、UPDATE、DELETE、NOOP）；Zep/Graphiti（三层图，每条边四个时间戳，矛盾时把旧边标为失效而不删）；Cognee（**未核**）。
  - agent 自己改：Letta/MemGPT 的记忆块；Anthropic 的 memory tool。
  - 后台 agent：Letta 新的 MemFS（git 管理的 Markdown 目录，文件树常驻提示词，`system/` 全量加载，其余按需；后台的反思子 agent 在 worktree 里写再合并，"defrag"子 agent 把记忆重排成 15 到 25 个文件）；Honcho 的 dream（至少 50 条新结论、距上次 8 小时、闲置 60 分钟才跑）；Mastra 的 Observational Memory（一个 Observer 把消息压成带日期和优先级的观察，一个 Reflector 再浓缩；每轮不检索，前缀可缓存）。
- **LoCoMo 不可靠**：对话只有 1.6 万到 2.6 万 token，没有"事实更新"类问题；1,540 个答案里 99 个（6.4%）是错的，评分模型接受了 62.8% 故意答错的回答（第三方审计，审计方自己也卖记忆产品）。
- **全文塞上下文不输记忆系统**：mem0 自己的论文（arXiv 2504.19413）里全文 72.90，Mem0g 68.44，Mem0 66.88，Zep 65.99，最好的 RAG 60.97。mem0 赢的是成本：p95 延迟 1.44 秒对 17.1 秒，约 1,800 对 26,000 token。
- **Letta 的"文件系统"结果**：LoCoMo 74.0%（gpt-4o-mini）。不是纯 grep：文件自动做了嵌入，agent 有语义搜索加 `grep`、`open`，规则强制先搜。Letta 自己的结论是 agent 多轮改写查询比检索机制更重要。自报，没找到独立复现。
- **LongMemEval（arXiv 2410.10813）**：ChatGPT 比离线阅读掉 37%。用抽取的事实替换原始会话，问答准确率下降。带时间的查询扩展把召回提高 6.8% 到 11.3%。Zep 在"助手说过的细节"上掉 17.7%（它自己的论文）。
- **独立或对照的结果**：
  - MemoryAgentBench（arXiv 2507.05257）：长上下文 48.8，BM25 41.5，嵌入检索 38.2，MemGPT 28.3，Zep 24.0，Mem0 21.1。准确检索一项 BM25 60.5 对嵌入 54.7。"选择性遗忘"所有系统都最差，多跳最多约 7%。
  - MemDelta（arXiv 2606.29914，单作者）：原文检索约等于全文（47.2 对 49.8）；agent 自己记 42%，低于基础检索的 47%；Mem0 在 6 类问题里 2 类追平云端检索，成本约 50 倍。
  - "Beyond Memory Leaderboards"（arXiv 2607.16848，作者里有自己的系统）：同等约 3 万字符预算下，简单检索 7.25，高于 Mem0 6.97、Hindsight 6.53、Cognee 5.28、Graphiti 5.27。在稠密检索上加 BM25 是单项最大的改进。
  - LongMemEval-V2（arXiv 2605.12493）：文件加编码 agent 的记忆 72.5%，最好的 RAG 48.5%，延迟高。
- **写入一侧**：热路径和后台的取舍只有"延迟对新鲜度"的说法，没找到对照的质量比较。后台压缩有最好的实测（Mastra 84.23 对自家检索 80.05，厂商自测）。
- **上下文腐化（Chroma 报告）**：测的 18 个模型在约 300 个相关 token 上都比在约 11.3 万 token 的全文上好；一条干扰项就降低准确率。
- **投毒**：MINJA（arXiv 2503.03704）只靠查询就能植入记录。Gemini 的延迟工具调用：文档里埋"如果用户说 X 就存这个"，写入发生在之后的用户轮（第三方，Rehberger）。ChatGPT 的 SpAIware、AgentPoison 的成功率 **未核**。
- **Markdown 知识库的做法**：
  - Karpathy 的 LLM wiki（gist）：不可变的原始资料、模型维护的 wiki、一份约定文件。操作是 ingest、query、lint（矛盾、过期、孤儿）。`index.md` 一页一行先读，`log.md` 只追加。他说只靠索引在"~100 sources, ~hundreds of pages"够用。
  - QMD（README）：SQLite FTS5 加 sqlite-vec，本地小模型做查询扩展和重排；`qmd search` 是纯 BM25，不加载模型。
  - grep 在多大规模失效没有对照数据，只有传闻（**未核**）。

## Anthropic 的两篇文章、一篇新论文和 Obelisk

2026-11-15 当天补的四个出处。前两篇是厂商自己的文章，实验都在 Claude 模型上做。

- **《Building always-on agents》（厂商，2026-11-13）**：常驻 agent 外围的五个部件是事件收件箱、定时器、记忆、许可、发件箱。记忆一节：
  - 存储是一个文件目录，落在持久存储上。
  - 记忆只放 agent 没法再查到的东西；别的系统里已经有的，存一个指针。
  - 四类：用户指令（单独一个文件，每次运行都加载）；用户笔记（先一个文件，多了拆开，只加载索引）；发过的消息（记下已经告诉过用户什么，避免重复）；任务进度（每个进行中的任务一个文件，只加载索引）。
  - 运行中写入是基础，dreaming（回看过去的会话，替换过期条目、找跨运行的规律）是可选的附加。
  - 压缩或开新会话都会丢细节，要留的东西沿途存进记忆。
  - 其余部件里和 operad 有关的：一个收件箱同一时间只有一个 worker，连发的几条消息合并成一次运行；定时器分 follow-up 和 schedule，触发时只往收件箱写事件；挂起的工具调用让运行结束、会话存下，回答作为事件回来再续上（和 ADR 0026 D6 同一个设计）；凭据由环境外的代理注入；发件箱建议先安静，用评测调发多少。
- **《The components of agent memory》（厂商，2026-11-06）**：
  - 新模型判断该记什么已经很好：玩 Pokémon 到一万步时，Sonnet 3.7 写了 413 个文件、225 个目录，拿到 1 个徽章；Fable 5 写了 9 个文件加一个 `global.md`，拿到 4 个。后者只记屏幕上读不到的东西（策略、计划、验证过的规则）。
  - 给强模型定死规则反而变差：规定"只记失败"后，Opus 5 和 Opus 4.7 从记忆得到的提升掉了一大半。文章的做法是告诉模型记忆是干什么用的，不告诉它怎么用。
  - 弱模型需要提示：Sonnet 4.6 不到一半的时候会先读记忆，提示它先读并验证猜想后分数接近翻倍；Sonnet 5 十次里九次自己会读。
  - 整理对着原始记录核对能改正写错的笔记：一条写错的笔记让 Claude 在同一处失败三次，整理时对照会话记录改正后通过。
  - 搜索加 wiki 好于单用任一种：约 35 万个文件的语料上，只用搜索 53%，只用 wiki 最高 48%，两者一起 61%，每题省约 2 万 token。wiki 对要跨多个文档的问题有用（87% 对 73%），对单文档能答的问题没有明显提升。
  - 常驻注入的那层要小：注入的错笔记会带进每个会话；整理的一大块工作是把细节往下挪、留下链接。
  - 多个 agent 写同一页会互相覆盖：共享一张表时 57 条事实留下 41 条；一个 agent 一页、原文逐字引用后 57 条全在。
  - 文章承认没解决的：整理要花算力，频率怎么定没有答案；有一个任务里 wiki 比原始文档还大。
- **arXiv 2610.30755（《Is Complex Agentic Memory Always Needed?》，2026-10-22，只读了摘要）**：对原始历史做朴素检索（稠密向量加重排，不是 BM25），在 LoCoMo、LongMemEval、MEME、MemoryAgentBench 的 7 组设置里 6 组第一，比最强的记忆系统高 0.13 到 5.53 分。即使完整访问加工后的记忆库，准确率仍低于原始证据。
- **Obelisk（厂商，`tommy0103/obelisk` 的 README；AGPL-3.0）**：
  - 只做索引：把本机 11 家 harness（含 Claude Code、Codex、Pi、Hermes）的原始会话读进一个 SQLite（FTS5）。
  - 没有固定的查询接口：一个 skill 教 agent 现场写 JS 查询脚本（`search()`、`sessions()`、`sql()` 等），跑完读 JSON 再回答。
  - 记忆层是缓存：检索得出值得留的结论时，agent 提议一个 Markdown 文件，人批准后才登记；README 称它是"a synthesis cache, not a replacement for raw evidence"。
  - 被压缩、分支、回退取代的历史标为 inactive，默认不查。
  - 贡献指南写明会话内容是攻击者可控的，流到 shell、文件系统、DDL 的一律默认拒绝。
  - 作者帖子里的另外几条（摘要和原子事实带来负收益；只用 BM25 和 grep 就基本解决准确率；图视图省 38% token）出自没读的两篇论文和他自己的 talk，**未核**。

## 各家收敛和分歧的地方

- **收敛**：
  - 一小块有上限、每次都进上下文的索引或画像，加一个按需取的大库。
  - 只追加的每日记录和整理过的主题笔记分开。
  - 模型写入不问人；批准只出现在团队共享的知识和管动作的规则上。
  - 规则和许可不放进记忆：Codex、Copilot、Windsurf、Cursor、Grok Bot、dots 都明说。
  - 后台整理在取代只追加的笔记。
- **分歧**：
  - 能不能看：文件（Claude Code、OpenClaw、Hermes、NanoClaw）好于主题列表（Claude），好于有损摘要（ChatGPT），好于完全看不到（dots、Grok 个人 bot）。
  - 当场写（Claude Code、Hermes、Grok）对后台合成（ChatGPT、Codex、Muse）。
  - 会话内冻结（Hermes，保缓存）对当场可见。

## 对 operad bot 的含义

这一节是判断，不是决定。

ADR 0026 D7 的方向有证据支持：文件加 agent 自己搜，不输抽取式和图式的系统，而且人看得见、改得了。要补的是四样：带上限的索引、可搜的原始记录、后台整理、来源标记。最弱的一点是"只用 grep"。其中布局、当场写、范围、规则这几条在 2026-11-15 读了上一节的四个出处后改过，记忆只放查不到的这条是新加的。

1. **布局用三层**：一个有上限、每次注入的索引；只追加的每日记录；按需读的主题笔记。OpenClaw、Claude Code、NanoClaw、Letta 新版、Karpathy 的 wiki 都收敛到这里。放进知识库插件的设计。
2. **bot 当场写笔记，只给很轻的指引；后台整理负责核对和收拾**。告诉 bot 记忆是干什么用的（只记查不到的：偏好、纠正、验证过的规则），不规定怎么记。整理是一个定时的 flow：对着 chat 记录核对笔记、合并重复、把细节从索引挪到主题笔记并留下链接，结果是一次 git 提交，差异可看可回退。
   - 来由：Anthropic 的实验里新模型判断该记什么已经很好，定死规则反而变差；整理对着原始记录能改正写错的笔记。
   - 相反的证据：MemDelta 里 agent 自己记得分最低。两边的实验设置不同，没有直接可比的对照。
   - 保留的防线：一次改写丢掉太多旧条目就作废（OpenClaw 的 25% 规则；Hermes #105921、#76035 是没有这条的后果）。跑在较弱模型上的 bot 要有"先读记忆"的提示。
   - 这一条原来是"当场只往每日记录追加，索引和主题笔记只由整理步骤写"，读了 Anthropic 的文章后放宽。
3. **先让原始记录可搜，整理过的笔记是第二步**。搜索用 SQLite FTS5，不用裸 grep，向量留作以后可选。chat 记录已经在引擎里，给它加全文搜索就是 Hermes 的 `session_search`。
   - 来由：对照实验支持的是 BM25 和对原始历史的检索，不是 grep；只存抽取的事实会丢细节；arXiv 2610.30755 和 Anthropic 的"搜索加 wiki"都把原文检索放在地基的位置。
   - 可以借鉴 Obelisk 的做法：不设计固定的查询工具，由一个 skill 教 bot 现场写查询；代价是要给查询一个只读的环境。
4. **压缩前落盘照 OpenClaw 的约束**：静默一轮，只许追加当天的记录，其他文件只读，没东西就不写。这是 chat 后续工作清单里已经列的事。
5. **每条记来源，不可信来源（网页、文档、工具输出）写的不进索引**。但不要学 OpenClaw 用哈希校验把整个文件排除：operad 的知识库就是要让人和 Obsidian 直接改的，它那两个未修的 issue 正是这样来的。
6. **记日期，新的取代旧的而不是删除**；整理步骤顺带查矛盾、过期和孤儿。遗忘是所有系统最差的一项。
7. **范围按 bot**；多人场合（群聊）不注入个人记忆。不是人当场发起的运行（定时、webhook）读它的 flow 需要的那部分（digest 要偏好和发过的内容），它写的东西按来源标记处理。OpenClaw 在群聊里由代码扣下 `MEMORY.md`，Hermes 不区分用户是它文档自己承认的弱点。这一条原来写的是后台运行一律不注入，和 Anthropic 文章里"每次运行都加载用户指令"以及 digest 的需要冲突，所以收窄到多人场合。
8. **规则不进记忆**：必须遵守的东西留在 access profile 和 bot 的说明文件里。记忆只帮助回想。
9. **dev 插件的 worker 先不做记忆**。同行基本没做，ETH 的研究说仓库上下文文件没提高成功率还涨了成本。值得留意的只有 Copilot 的"用前核对引用"和 Codex 的离线合并。"上次这个问题改了哪些文件、为什么"这类问题不需要记忆，一个能搜 operad 历史的 skill 就够，历史本来就记着每一步做了什么和为什么。
10. **记忆只放查不到的；operad 里已经有的存指针**。计划、任务、历史不抄进记忆。digest 要记下发过什么，避免重复推送（Anthropic 文章的"发过的消息"一类）。

要 owner 定的：

- **写入要不要人批准**。同行大多不问。倾向不问，靠 git 记录和整理的差异事后看。
- **FTS 索引是否从知识库插件第一版就带**。倾向带。
- **注入是否像 Hermes 那样会话内冻结**。冻结能保住提示缓存，代价是当场记的东西下个会话才生效。
- **整理多久跑一次**。Anthropic 承认频率没有答案，整理要花算力；OpenClaw 是每天一次。

# Grok Bot 和同类产品：定位、功能，以及对 operad bot 的含义（2026-11-11）

`operad-bot.md` 把 `assistant` 改名为 `bot` 的同一天做的调研。事实和判断分开写：前四节是事实，标 **厂商** 的读过厂商的页面或文档，标 **第三方** 的只有第三方出处，标 **未核** 的没找到可靠出处；最后一节是判断，都还不是决定。

## Grok Bot

- **定位（厂商）**：2026-08-11 发布，当时标 beta。原话是 "your team of always-on agents"、"AI teammates you can give real work to"、"your AI teammate with a computer"。账号、计量和连接器的 token 都在 Cursor 一侧。
- **bot 这个对象（厂商）**：新建只要名字和头像，角色和指令不是字段，在对话里告诉它；个人 bot 没有设置页。有一个 "primary Bot"，主动来问、协调别的 bot。Team Bot 像文档一样共享，每人的对话私有，角色分 Owner、Manager、Collaborator。
- **电脑（厂商）**：一个账号一台常驻的云端电脑（浏览器、命令行、文件系统），所有 bot 共用，各有自己的屏幕；文档明说屏幕 "are separate work surfaces, not separate security boundaries"。在用户本机执行默认关闭。
- **工具和通道（厂商）**：连接器（Gmail、Notion、Slack 等）、插件、自定义 MCP、Vault 和 1Password 登录、把写代码交给 Cursor Cloud Agents。通道是桌面、网页、手机 app（带语音）、X、Slack、Teams，每个 bot 一个邮箱地址。没有 Telegram 和短信。
- **触发（厂商）**：routine，用自然语言写时间表，或由 Slack、GitHub、Linear、Sentry、PagerDuty、来信、webhook 触发。每个 bot 50 个，间隔至少五分钟，只留最近 20 次运行记录。
- **许可（厂商）**：默认开 Auto Review，另一个模型审 shell 命令、app 调用、电脑操作，结果是放行、询问或拒绝。询问是一张卡：操作和输入，三个按钮（允许一次、总是允许、拒绝）。后台运行的卡 30 分钟过期。用户可以写各 20 条"先问"和"自动允许"规则。后台发邮件只存草稿。模型拿不到保存的密码和卡号。审计日志只有企业版有；操作录像默认关。出网默认全放行。
- **记忆（厂商）**：每个 bot 自己的记忆（偏好、规则、带日期的工作日志）。个人 bot 没有记忆页面，只能在对话里问它记得什么、让它改或忘。
- **价格（厂商）**：含在每月 30、100、200 美元的订阅里；每周一个用量池，用完走预付或按量，月上限 "isn't a hard stop mid-run"。不能选模型。
- **用户遇到的问题（第三方）**：
  - 费用失控：Cursor 论坛上有人十分钟用掉 27 美元，一周的 Ultra 额度八小时用完；官方承认并重置过一次。
  - VelvetShark 五天跑 67 件事：40 件自己完成，14 件要人帮，5 件做了一半，8 件失败或取消。一个只该读推文的 bot 执行了写命令，从他的账号发了帖；一个 routine 显示"中断"，帖子其实已经发出；电脑更新两次悄悄去掉了他装的同步工具。
  - Latent Space：看不到模型路由和上下文管理；一个 bot 一条长对话，不相干的事混在一起；共用登录态，一个 bot 的错不被隔离。

已知的安全问题（第三方，没读一手报告）：OpenClaw 的技能市场出过成批的恶意技能（几百到上千个，装窃密木马）、一个点链接就能远程执行的漏洞、几万个暴露在公网的网关；Hermes 的注入扫描被绕过，接口缺认证；NanoClaw 有四个 CVE，其中一个能读宿主机文件。

## 这一类产品现在长什么样

- 对象收敛到同一个形状：一个有名字的 bot，带记忆、定时或事件触发的例行任务、一台电脑、许可规则和活动记录。Grok Bot、dots、Rakazo、OpenBot 都叫它 bot 或近似的名字。
- 托管一侧卖的是省心：登录即连，电脑有人维护，手机上随处可聊。代价是不能选模型、看不到上下文管理、费用没有硬上限、bot 之间没有安全边界。
- 自托管一侧卖的是控制。OpenClaw 和 Hermes 默认在宿主机上放任地跑，安全事故都出在这里；后来者（NanoClaw、Rakazo、OpenBot）的卖点正是把隔离、密钥和许可做成默认。
- 许可的通行做法是三档（问、由模型判、不问）加一张三个按钮的卡。后台运行的询问普遍处理得差：过期（Grok Bot 30 分钟，Hermes 300 秒）或者直接拒绝。
- 历史和审计普遍弱：Grok Bot 只留 20 次运行，审计只给企业版；OpenClaw 没有。

## 判断（第 4、5 条 2026-11-11 owner 已定，写进 `docs/backlog/operad-sandbox.md` 和 `docs/backlog/operad-bot.md` 的待办；其余未定）

1. **位置**：operad 的 bot 在自托管、默认不放任这一格，和 NanoClaw、Rakazo、OpenBot 同一格，不是 Grok Bot 那种托管的云端电脑。和它们的差别是三样已有的东西：每一步都在历史里（别家最弱的一项，我们不用另做）；询问是待处理项，不过期，答了从原处继续（ADR 0008 D1 到 D5）；harness 可选（Grok Bot 被抱怨最多的是不能选模型）。
2. **对象要不要就叫 bot**：这一类产品的对象都是"一个 bot"。现在的决定是插件叫 `bot`、对象叫 profile，用户要记两个词。可以让对象类型就是 bot，去掉 profile 这个用户词（`bot:chat <bot>`，配置里 `bots.default`）。这要改 ADR 0030 D1，等 owner 定；T-0303 排在 T-0279 之后，来得及并进去。
3. **例行任务就是 flow**：别家的 routine 对应我们的定时 flow（`digest:run`、`brain:review`）加通道事件。不新增用户词；要补的是在一个 bot 上列出它的定时 flow 和最近的运行。
4. **后台运行更严**：不是由人在这个 chat 里的一句话发起的运行（定时、webhook、来信），对外写的动作一律先问或只存草稿。Hermes 的定时任务默认拒绝、Rakazo 对 webhook 发起的运行更严、Grok Bot 的后台邮件只存草稿，都是这条；发错推文的事故也出在这里。放进 `operad-sandbox.md`。
5. **费用硬上限**：每个 bot 一个周期预算，到了就停在当前步骤并进待处理，不是事后提醒。Grok Bot 最多的抱怨是这个。
6. **边界是 bot，不是屏幕**：每个 bot 自己的目录和访问档已经是这样（ADR 0030 D1、D2），保持；不做多个 bot 共用登录态。
7. **记忆看得见**：记忆是知识库里的 Markdown（`docs/backlog/operad-bot.md` 的知识库条目），用户能打开、能改。Grok Bot 没有记忆页面，这是现成的差别，保持。
8. **密钥**：来源插件已经不让 agent 碰密钥（`docs/backlog/operad-bot.md` 的来源与密钥条目）。bot 自己要用登录态时，照 NanoClaw 和 Rakazo 的做法由插件在请求时注入，不进环境变量。以后设计。
9. **不做**：云端电脑、桌面和浏览器操作、多个 bot 的群聊、Team Bot、技能市场、由模型代人批准（Auto Review 一类）。前四项是托管产品的地盘；后两项是别家事故的来源：技能市场见 ADR 0011 D2，模型替人决定见 `docs/backlog/operad-bot.md` 的不做条目。

## 技能和 MCP

第二轮调研，问的是别家怎么处理技能、MCP、插件和 bot 的自我扩展。出处同前，另加各家的 skills、MCP、plugin 文档页。

**技能**

- 格式：一个目录加 `SKILL.md`（name、description）。OpenClaw、Hermes、NanoClaw、dots、Cowork 都是；Grok Bot 和 Rakazo 没写明格式。
- 进上下文：只列名字和描述，正文用到时再读。OpenClaw 每个技能约 24 token；Hermes 分三层。Hermes 的 issue #22620：243 个技能，每个任务约 8 万 token。
- 谁写：用户；在对话里"把刚才的做法存成技能"；演示一遍让 bot 记下来（Grok Bot、Rakazo、dots）。
- bot 自己写的：Rakazo、OpenBot 先成草稿，人点了才生效；Hermes 默认直接生效（`skills.write_approval` 要自己打开）；Grok Bot 的个人 bot 不设卡。
- 脚本：Rakazo 导入的技能只当说明读，脚本不跑；OpenBot 的技能"是说明，不是能力"；OpenClaw 默认在宿主机上跑；NanoClaw 的容器技能只读挂进容器。
- 范围：Grok Bot、Rakazo 是账号下所有 bot 共用一个库；OpenClaw 有每个 agent 的允许列表；Hermes 按 profile。
- 市场和互相导入：OpenClaw 有 ClawHub，也能从 git、npm、Claude 兼容的市场装；Hermes 能从 Skills Hub、GitHub、skills.sh、ClawHub 装。ClawHub 出过成批恶意技能，加了扫描后仍被绕过（第三方）；Hermes 的扫描器是正则，被绕过一次（第三方）。

**MCP**

- 怎么加：托管产品在界面或对话里填 URL 或命令，不写 JSON；自托管的用配置文件加命令行。
- stdio 服务跑在哪：Grok Bot 在云端电脑上；Hermes 是本机子进程，只拿到显式配置的环境变量；NanoClaw 大概在容器里（**未核**）。
- token：Grok Bot 在 Cursor 的后端，bot 调工具时拿不到；Muse 在 VM 里，agent 看不到真 token；NanoClaw 由 vault 注入出站请求；Rakazo、OpenBot 由后端注入。OpenClaw 在宿主机上对模型不设防。
- 工具调用的许可：Cowork 每个工具三态（总是允许、要批准、禁止），按读和写分组；Hermes 按服务设 `trust`，`untrusted` 时写的要问；OpenBot 把不认识的工具和自定义服务的工具一律当写，没有策略就什么都不许；Grok Bot 没有按工具的设置，靠审核模型加用户规则。
- 工具多：Cowork 十个连接器以上可以按需加载；Hermes 的 `lazy` 首次调用才启动服务；其余没写。
- 注入：都把外来内容标成不可信的资料，都承认只能减轻。Muse 让读过用户数据的进程失去自动出网的许可。
- 范围：托管产品是账号级，所有 bot 共用；NanoClaw 按 group；OpenClaw 按 agent 记授权。

**插件和自我扩展**

- 插件是打包单位：dots 的是技能加 MCP 服务（加钩子）；Cowork 的是技能、连接器、子 agent。OpenClaw 和 Hermes 的插件是进程内代码，能加通道、模型、harness、工具，文档自己说装插件等于跑代码。
- bot 自己装：Grok Bot 能自己装应用、加 MCP 服务、存技能，只有私网的服务先问；NanoClaw 装包、加 MCP 服务、改自己都要人批，没人可批就拒绝；Rakazo 改 bot 的指令或模型一定出卡。
- Grok Bot 的毛病（Cursor 论坛，第三方）：自定义 MCP 的 OAuth 常失败；一个没响应的连接器拖垮所有 MCP 的发现；更新电脑清掉 bot 装的包。

**判断（2026-11-11 owner 已定）**：写进 ADR 0030 D4、D5、D7，以及 `docs/backlog/operad-bot.md` 和 `docs/backlog/operad-sandbox.md` 的未定部分。
